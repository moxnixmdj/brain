# Brain: software-engineering problem inventory

**As measured on 2026-10-29.** Working branch: `arena/4ca3a720-brain`, based on `d2ba13c7`, with the local safeguards and probes described below. This is the complete list of *identified* issues from this audit, not a claim to know every undiscovered defect. The objective is the owner's: a highly capable, reliable, resource-efficient, autonomous software engineer, without AI models in Brain-credited producer cognition. PDF, office, image and chart work is deliberately lower priority.

**The main constraint is trust, not a shortage of names in a registry.** Some real mechanisms exist and work on bounded examples, but several success and independence claims can be produced without the corresponding work. Until those boundaries are repaired, high capability counts and green-looking results cannot establish a reliable autonomous engineer.

## Critical: truthful completion and verification

### 1. Fabricated raw-acceptance receipts — false success blocked, authenticated path absent

`lossless_raw_task_acceptance_gate_v1` checks hashes, schemas, and self-described verifier identities and semantic flags but cannot authenticate them. In `execution_guard/acceptance_receipt_authenticity_probe_v1.py`, **4/4** constructed delete/modify/copy/compress requests previously passed the gate and authorized route-C direct admission with caller-written receipts although no requested effect occurred. After the fail-closed change, **0/4** pass or authorize route C. This is a direct API counterexample, not a demonstrated live-front-door exploit.

Complete, consistent receipt sets are now reported as **unresolved**, with zero accepted obligations and separate structural diagnostics. This blocks false success but also prevents *all* receipt-only successes in this gate, including potentially legitimate ones. A usable positive path requires an independently authenticated verifier authority tied to the exact task, candidate and evidence; another string or hash is not enough. Other admission routes and receipt consumers have separate trust assumptions.

### 2. Projected capability admission accepted unsigned OIDC claims — false admission blocked; positive path unavailable

`live_integrated_brain_v1._receipt_admits` previously accepted plain dictionaries without signature verification. In `execution_guard/oidc_claim_authenticity_probe_v1.py`, **4/4** invented references were admitted, including an unrelated repository, mismatched run ID, and untrusted workflow. The loader now reuses the receipt lane's existing fail-closed attestation decision: **0/4** are admitted. Four direct tests additionally exercise both extended-registry and projection entry paths. These disposable cases are not proof a real registry was altered.

The separate receipt issuer already returns before executing receipt-specified code or writing verification records when a run reference is unauthenticated. Its workflow preflight deliberately fails before receipt code or artifact publication. No authenticated, result-bound positive path is currently available: genuine references are also refused. A future positive path must bind a trusted attestation to the exact module, result, verifier and execution policy; a signed identity claim alone is insufficient.

Before the loader change, **295 of 305** projected entries passed its structural check; their references had no `token`, `jwt`, `id_token`, or `signature` field. This does **not** prove those historical runs were forged. After the user-approved PR registration deferral, the current live loader admits **128 curated entries and zero projected entries** (previously 165 curated); those 295 previously admitted projected entries are no longer available through this loader, even if genuine. No source or evidence files were removed. The curated static registry still uses a separate status-based path and is not independently authenticated by this change. Reverification/migration is required before claiming the projected capabilities are available again.

As limited defense in depth, the receipt workflow now scopes automation-app secrets to its landing step, disables checkout credential persistence, makes its GitHub token read-only, and unsets the decoded token response before the preflight. These changes are **not** process isolation: any future re-enabled execution would share the runner and job-level OIDC authority with landing. Static checks and local YAML parsing pass; no GitHub Actions execution of this change has been observed here. Runtime evidence labels now describe the legacy admission as unauthenticated rather than GitHub-attested.

### 3. Registry-only composers claimed completed engineering tasks — locally fail-closed; no execution path

`execution_guard/registry_only_composition_probe_v1.py` selected **14** bound adapters whose source matched `verified = all(found.values())` and ran them in a disposable root containing only a copied registry and output directory. Previously **13/14** returned `verified=True` despite having no source project, executed tests, diff, or PR. After a local fail-closed change, the same probe observes **0/14** verified claims and no adapter errors. All 14 now expose registry readiness as a diagnostic and refuse verification because they do not execute dependencies. A separate 28-case test exercises each adapter with an empty and a fully populated synthetic registry; the latter also supplies the file whose absence made the fourteenth adapter refuse in the original probe. These 14 adapters now always refuse, even when a real workflow might otherwise be desired: no dependency-execution or authenticated positive path has been implemented. Historical static status/verification metadata remains stale; limitations were amended, not treated as a substitute for corrected authority.

This is a bounded source-pattern family, not a census of every composer. Separately, `software_repair_crossfile_choreograph_v1` claimed a verified repair merely after importing three modules. Four fixtures (missing, empty, syntactically broken, and root source paths) all falsely verified before its local mitigation; it now reports unverified. Its historical registry verification metadata remains stale, and this mitigation does not implement a repair pipeline. Preserve useful implementations, but require actual dependency execution and independently checked outputs before calling a composed task verified.

### 4. Whole-task acceptance was crediting instructions never performed — mitigated conservatively; functionality remains incomplete

The generic raw-trace verifier inspected individual steps but could mark *all* source obligations accepted. In `raw_acceptance_obligation_gap_probe_v1.py`, **8/16** constructed single/compound traces accepted an unperformed follow-up before the latest safeguard; after it, **0/16** do. A further **4/4** requests using a real archive-verification step also falsely accepted an unperformed follow-up; `raw_acceptance_uncovered_inspectors_probe_v1.py` now reports **0/4** after the broader generic safeguard. These are direct-verifier tests, not demonstrated live-front-door exploits.

Current generic behavior remains intentionally cautious: multi-step traces, implicit shell phrasing without bounded whole-sentence proof, and other single-capability inspectors without whole-goal proof remain **provisional**, even when actual work completed. Genuine bounded single-archive create/verify forms can now be accepted after the local reinspection described in #5, while appended instructions remain provisional; the earlier two archive-positive failures are fixed. Other real-positive losses remain: a Python audit and two lower-priority XLSX/DOCX learning cases still expect full acceptance but are provisional in the current workspace. This is not complete per-obligation whole-goal verification.

### 5. Corrupted archives falsely accepted — local artifact check strengthened; trace authentication still open

The archive compound verifier previously accepted **4/4** forged successful traces for archives with corrupted member bytes, while the real GNU-tar adapter rejected them. After reusing a shared strict check, the updated direct probe observes **0/4** unsafe acceptances even with forged current archive digests. Create, verify, compound and the original single-goal acceptance now derive exact membership from the manifest, compare each member to current source bytes, bind the parsed manifest to those bytes, refuse symlinked path components, and validate the full gzip stream. Six previously accepted damaged-gzip variants now have regression tests. Four additional ancestor-symlink cases failed before the latest path check and now pass. The archive-specific world binder skips unrelated or unusable discovered manifests while preserving explicitly named inputs.

These are **local state checks**, not authentication that a claimed step executed or protection against concurrent malicious writers. Inference selects a qualifying candidate, not proof of user intent. Strict acceptance requires a `records` list even though adapters permit absent/null `records`; such inputs remain provisional. Archive product work is low priority, but the false-acceptance pattern matters elsewhere.

### 6. Reinspection can itself be dangerous; containment is limited — partially mitigated

Earlier disposable-tree tests demonstrated file mutation during reinspection through `find -delete`, `sed` write commands, attached `sort` output flags, and a repository Python writer. The existing `zero_ambient_namespace_launcher_v1` and read-only query wrapper are now used for bounded reinspection, with no unsafe host-execution fallback. A forged stdout destination with a recomputed hash is also refused after byte comparison. Focused prior security tests: **112 passed, 3 pre-existing failures deselected, 2 subtests passed**.

This is a mitigation for the inspected replay paths, **not** a claim that arbitrary producer code, tests, plugins, PATH contents, network, resources, or every inspector are safely isolated. Effective inspector coverage across real tasks is unknown. The previously asserted 192/267 coverage bounds were invalid and are withdrawn. In `execution_guard/confined_pytest_feasibility_probe_v1.py`, the existing launcher and query wrapper ran real pytest in a read-only input and in a copied writable private worktree: **4/4** runs of each four-case fixture passed, including bounded checks of host-path and host-TCP inaccessibility, input read-only behavior, and private scratch writes. A real failure and all-skip report were correctly distinguished using the existing JUnit parser. However, a constructed plugin both forced exit 0 and overwrote the JUnit report with a fabricated passing case: the simulated existing JUnit verdict accepted it although pytest stdout showed a failing test. This is one constructed plugin counterexample, not a general exploit rate. The launcher is **not integrated into the issue-to-PR gate**; confinement does not authenticate in-process test evidence, and the successful fixtures do not establish complete security.

The issue-to-PR orchestrator formerly checked only Python files and did so **before** pytest. In `execution_guard/issue_to_pr_integrity_probe_v1.py`, four deliberately mutating pytest fixtures changed the original Python source, build configuration, dependency lock, or CI workflow; **4/4** were still reported `verified=True`. The local change inventories the non-excluded source tree and checks again after pytest: **0/4** are now reported verified, but all four writes still occurred. It cannot prevent or undo writes, detect changes restored before the check, inspect excluded cache/git directories or external symlink targets, or prevent writes elsewhere. This is a direct-adapter experiment, not proof of front-door exploitability; untrusted code still has inherited caller authority and needs real isolation.

**jq ambient-authority defect, locally mitigated:** the direct `jq_query` adapter's previous filter checks allowed bare `env` in four constructed variants and bare `input`; using a synthetic test marker, these ran rather than being refused. The subprocess inherited the caller's environment. The adapter now rejects these primitive names, runs jq with an empty environment and closed stdin, and the existing confined-replay wrapper applies the same checks and respects the empty-environment request. Two direct object-field controls remain usable, a test that bypasses the lexical filter sees an empty child environment, and the existing mediated namespace jq test passes. These are bounded controls, not proof that arbitrary jq is sandboxed: regex matching may reject harmless quoted keys, filesystem/PATH authority and resource limits remain separate, and jq installed only outside the default executable search path may no longer be found. The full focused group reported **125 passed / 2 deselected** with `/usr/sbin` on PATH; the deselections concern absent `sqlite3` and an unavailable optional module. No front-door exploit was demonstrated.

## Critical: tests and evidence

### 7. Static test selection and false-green gates — bounded mitigations

`impact_selection_safety_probe_v1.py` constructs four disposable Python projects. In **4/4**, the original full suite was green, the selected subset stayed green after a breaking change, and the full suite caught the regression; examples exercise indirect imports, reflection, wildcard dependencies, and pytest fixtures. This is not a corpus-wide miss rate. The static selector remains useful as an **advisory** tool and now labels its scope accordingly; it does not prove that omitted tests are unaffected.

The issue-to-PR orchestrator runs pytest's configured **default discovery** and records a local diagnostic only when exit code is zero, at least one JUnit-reported case passes, and zero cases fail. Missing pytest, no tests, all-skipped tests, timeout, and missing/malformed reports fail that diagnostic. The selected slice remains advisory. Following the JUnit forgery finding below, **the composite `verified` field now always fails closed** because no authenticated test-evidence path exists; even genuine green runs remain provisional. `local_test_report_passed` is explicitly unauthenticated and must not be used as verification. This covers only tests discovered by the project's configured pytest invocation; it does not establish correctness of uncollected tests, other languages, or external checks.

An additional **4/4** constructed all-skipped suites spoofed the initial implementation by printing `1 passed` or similar text. JUnit parsing and checking both exit code and reported failures catch those examples and a plugin that only overrides the exit code, but do not authenticate reports. In `execution_guard/issue_to_pr_junit_forgery_probe_v1.py`, a plugin that also replaced JUnit with an invented passing case caused the issue-to-PR adapter to report **verified=True** for a deliberately failing test; the local fail-closed change now reports **verified=False**. Four fabricated report shapes similarly went from 4/4 verified to 0/4 verified. The same report-forgery mechanism was then reproduced against the full-test, coverage and mutation gates using four case-name variants each: **12/12** falsely returned PASS before, and **0/12** after applying the same fail-closed boundary. All three expose `local_gate` as an explicitly unauthenticated diagnostic and return UNRESOLVED for a local PASS. This necessarily makes genuine passing runs provisional as well, and pytest still runs with host privileges. These direct-adapter examples do not establish front-door reachability or general rates. The same forgery succeeded in a confined feasibility fixture, so confinement alone cannot authenticate pytest's in-process report.

The separate pre-merge `python.repo.diff_apply_full_testgate` also falsely accepted **2/4** skip/xfail fixtures and a forced-zero failing suite; the other two skip fixtures were already refused because pytest returned a nonzero exit. It now reuses the flake detector's JUnit parser, requires a passing case and no reported failures, and refuses missing or invalid reports. A duplicate-ID test proves an earlier failure is not overwritten by a later pass. The existing flake detector now conservatively collapses duplicate IDs to the worst result per run, but still cannot detect variation within one run.

The diff coverage gate formerly returned verified `PASS` and 100% for **9/9** constructed cases: four unimported-file paths, one configured omit, one non-Python diff, two all-skipped/xfail runs, and a forced-zero failing run. After the initial missing-file fix, **3/4** constructed coverage-exclusion cases still falsely passed; the fourth already failed because of a separate uncovered line. The gate now checks JUnit outcomes and refuses missing changed files, excluded hunk lines, zero executable hunk lines, and non-Python-only changes as verified coverage. Coverage configuration and pytest discovery remain in scope, hunk ranges include context, and line coverage is not behavioral proof.

Four existing diff gates also reused deterministic scratch paths and collided during concurrent identical-diff runs: **16/16** constructed two-thread pairs failed before their respective fixes, and **16/16** completed after unique scratch directories were introduced. These pairs used distinct output paths; shared output paths, malicious concurrent writers, and arbitrary broader concurrency are not addressed. None of the gates is a sandbox: pytest/git/coverage inherit substantial ambient authority, and JUnit/coverage reports are not authenticated.

### 8. Claimed never-miss and test-pipeline verification lacked execution — partially mitigated

The old `test_slice_never_miss_v1` emitted `never_miss=True`, “50/2000” and “40x” without actually selecting, timing, or running the tests; it even returned `verified=True` with an empty registry. `python_test_pipeline_verifier_v1` similarly checked registry names, not an executed pipeline. Both now return diagnostic refusals rather than claiming verified work. Their registry limitations were corrected, but their **static `VERIFIED_BOUND_CAPABILITY` statuses and historical verification fields remain stale**; downstream registry-only composers can still misinterpret them. No replacement pipeline or authenticated never-miss proof has yet been built.

### 9. Evidence pointers and declared status are not sufficient — open

Before the registration deferral, `capability_evidence_probe_v1.py --audit-pointers` reported **123** entries with a checkable pointer, **34** verification blocks without any pointer, and **8** dangling pointers among 165 static entries. A pointer existing is not itself proof of correct or independent execution; a dangling pointer is an unsupported claim, not proof the underlying code cannot work. ## Engineering workflow and breadth

### 10. The issue-to-PR loop is not a complete autonomous PR lifecycle

The existing Python orchestrator copies a source tree, applies structured `rename_symbol`/`move_symbol` choreographies, checks a fixed point, runs configured pytest discovery, and writes a diff plus PR intent. Its own contract does **not** push or open a PR, and its structured edit vocabulary is bounded. Free-text issue parsing is a separate adapter. Composite verification is currently unavailable even for genuinely passing suites: diagnostic results are not authenticated. The registry's static verified status and historical receipt fields are not a current authenticated positive path. A local passing test suite does not prove a correct bug fix, review, CI, conflict resolution, merge, or deployed behavior. Other git/PR tools exist; their complete end-to-end composition for arbitrary issues has not been demonstrated here.

**Move-path creation defect, locally mitigated:** before validating the move plan, the direct adapter staged `to_module` relative to the worktree without confining it. In `execution_guard/issue_to_pr_integrity_probe_v1.py`, **4/4** constructed traversal/absolute targets created previously absent empty files outside the worktree; two were outside the repository root. The adapter subsequently refused each request, but the side effect remained. The local change validates all edit paths before staging and again against the copied worktree; **0/4** probe destinations are now created. This is not a concurrent-writer or test-execution sandbox; the probe does not show overwrite of existing files or establish a live-front-door route.

### 11. Composition, binding, and trace identity remain incomplete

A prior multi-step chain was blocked by missing `et_xmlfile`, not proof the composition algorithm was invalid; its error classification now identifies environment blockers. Separately, the source-pattern composer test in #3 demonstrates false verification without execution. These are different issues. The earlier F13 spool example previously reported `FAIL_CLOSED__NO_OBSERVED_EFFECT`; a fresh focused run here instead stopped at `BLOCKED__CAPABILITY_DAG_ENVIRONMENT_BLOCKER`, so its present underlying behavior remains unmeasured in a fully provisioned environment.

Prior focused tests showed `TRACE_HAS_NO_CAPABILITY_ACTIONS` despite an action, blocking reinspection; three such failures predated these local changes. A real execution trace, its plan identity, and independent acceptance must line up.

### 12. Routing can choose the wrong act or ignore a binding refusal

A repair/acceptance request has been observed selecting `python.repository.acceptance.measure.v1` rather than `python.software.repair.measured_acceptance.v1`; nearby capability names do not prove the requested act was performed. Four direct admission cases (source index, full testgate, issue-to-PR and archive) previously returned both `typed_binding_refused=True` and `admitted=True`. They now refuse the route with the actual binding reason; fully bound source-index and archive routing controls remain admitted. An additional direct explicit-capability-name case also previously bypassed a real binding refusal; it now refuses, while its fully bound named control admits. This applies when the existing typed checker actually returns `BINDING_REFUSED`; it does not prove behavior when the checker errors or makes another kind of decision, or establish front-door reachability of these constructed cases. The focused `test_f1_best_candidate_that_cannot_bind_fails_closed_instead_of_falling_through` still fails separately in the front compiler. Act/object/argument arbitration needs further work, not an assumption that every act has only one owner.

An additional software-tool input integrity defect was found in the existing `jq_filter` binder: four unquoted filters containing array iteration, a pipe, arithmetic, or `//` were reduced to different prefix programs. The jq-specific binder now preserves quoted programs and simple bare field paths, and refuses the four complex unquoted forms rather than silently changing them; escaped closing quotes are also refused instead of returning a prefix. Quoting a complex filter is required unless and until a complete boundary/unescaping contract exists. Direct binder and real jq-contract binding tests cover these cases; they do not prove end-to-end execution. On four inspected requests the front compiler originally selected `vcs.git.rebase.v1` instead of jq, but route admission refused all four; no rebase was executed. The existing jq registry keywords now include `jq`, `filter` and `apply`, so those four quoted requests select the existing jq adapter and pass typed admission. Four disposable fixtures then ran that adapter with the exact bound filters and checked their output bytes; this is a compiler/admission/adapter test, not a `solve()` end-to-end verification. Four unquoted complex filters remain refused at compilation or admission. An old-versus-new registry-keyword comparison on 23 existing benchmark goals showed zero changed compilation selections or failure codes; this is a bounded check, not a general regression guarantee. The jq, routing, act-owner, front-door parity, named-input and issue-to-PR focused tests reported **94 passed**. The unrelated numeric-expression prefix issue remains open.

The fail-closed decision changes behavior: a test expecting an unbound symbolic math expression to reach the executor now fails earlier at route admission. A broader run immediately after the first part of this change reported **65 passed / 15 failed / 4 skipped**, including that changed diagnosis and F1; some other failures need the unavailable projected entries, and no complete baseline comparison was performed. After the explicit-name safeguard, the two new guard files plus act-owner and front-door parity tests reported **42 passed**. These numbers do not establish the route change has no other regressions.

Prior generated-goal reachability was **454 bound / 3 by explicit ID / 1 routed elsewhere / 1 not reached** out of 459 visible entries. The two miss examples are generated sentences for `vcs.git.log.v1` and `python.repo.pr_realize.v1`, not proof that no possible sentence can reach them. Naming mode's **21 `NO_SENTENCE`** rows were generated by an instrument that requires a destination even for verifiers; they are not 21 proven unreachable capabilities. Previous benchmark selection was **22/23** canonical and **21/23** front door; this is selection, not end-to-end correctness. An archive-specific routing family reached **8/8** after earlier act/synonym fixes.

**Rename-symbol safety:** the direct Python rename adapter modified cross-file local bindings in four constructed shadowing cases (parameter, lambda, conditional assignment and comprehension). This is conservative, not complete binding analysis: other target-module shadows, module aliases, dynamic uses and `complete` claims remain unproved.

**Rename linked-file and report integrity:** in four disposable direct-adapter fixtures, Python source-file symlinks or hard links let a cross-file rename modify a file outside the repository, despite the unverified result. The adapter now reuses the existing symlink-component check and refuses multi-link Python files before reading or writing; all four fixtures are refused without changing either source or external bytes. Four prior report destinations also overwrote a defining/other Python source, an external hard link, or a symlink target; six current tests including source configuration and a symlinked output-directory ancestor now refuse before edits. Existing report files inside the source tree are also refused, including legitimate ones; regular single-link reports outside it remain usable. These are direct-adapter cases, not demonstrated live-front-door exploits. Concurrent file replacement, races, symlinked source-directory traversal/completeness, test-code writes and filesystem behavior remain unresolved. The link/output guards and related rename, choreographer, issue-to-PR and selection suites reported **97 passed** locally.

A named pytest run also left adapter edits in place on four subprocess failure fixtures (missing executable, directory executable, non-executable file and timeout). A genuine green test run is also provisional, so no authenticated positive path was added. Pytest still runs with ambient host authority. The two guards, existing rename, cross-file choreographer, issue-to-PR and impact-selection groups reported **86 passed** locally; no front-door reachability or full-suite pass is claimed. The lexical instrument checked 135 engineering act labels against 165 static entries: **69** substring `provides` matches, **28** keyword-only, **38** no lexical match. ### 15. Speed and learning are not established at the owner's target

Prior n=12 warmed microbenchmarks on this host measured median reinspection times of **0.183 ms** for byte-reopen `cat`, **0.156 ms** for `wc -l`, and **116.692 ms** for confined `sort`. They are not end-to-end speed rankings.

A separate **8-per-arm**, warmed, alternating, serial synthetic pytest measurement with one selected plus 30 unrelated trivial cases measured medians of **180.16 ms** for an unsafe selected subset and **211.88 ms** for default discovery. The arms ran 1 and 31 cases respectively, both with JUnit reporting. This measures pytest invocation on one fixture, not end-to-end orchestrator cost or general performance (`issue_to_pr_verification_cost_probe_v1.py`).

After the latest fail-closed changes, an **8-per-arm** warmed serial synthetic fixture with 31 passing cases measured pytest-only medians **186.89 ms** without JUnit and **188.73 ms** with JUnit. The current full test gate measured **205.46 ms**, the coverage gate **510.99 ms**, and the mutation gate **440.52 ms** with its sample capped at one mutant.
