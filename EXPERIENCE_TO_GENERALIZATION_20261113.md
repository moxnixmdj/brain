# From experience to generalization: what is real and the next experiment

Date: 2026-11-13. This is a producer assessment, not independent verification.

## Answer

A good demonstration is useful evidence, not a guarantee. A single example is compatible with many different rules: if `x + 1` became `x + 2` once, it does not establish whether all increments, only a particular function, or only that particular input should change. An agent must infer which differences matter and check consequences in the new environment. An action can also depend on hidden state, permissions, version-specific APIs, or a side effect absent in the example. No finite set of demonstrations establishes correctness on all future computer tasks.

Persistent external memory, executable skills, and context can change an agent's behavior without changing model weights. Fine-tuning or reinforcement learning can also produce persistent weight changes and may improve transfer, but neither is necessary for all useful transfer nor sufficient for reliable universal transfer; it can introduce forgetting and other regressions. A stored record is not necessarily recalled, applicable, correct, or permanent. The project has not established sentience; consciousness is a distinct, unresolved scientific question, not a consequence of learning or agency. Theory-derived indicators are proposed evidence, not a definitive test ([Butlin et al.](https://hal.science/hal-05373552/file/Butlin-etal-TiCS2025.pdf)).

## What this checkout demonstrates

`canonical/swe_kernel/taught_actions/edit_by_example_v1.py` learns restricted Python AST transformations from before/after examples and refuses some ambiguous applications. The bundled workflow stores executable program text; this is not evidence of model-weight updates or a general GUI agent. `LEARNING_ONCE_DOES_NOT_SOLVE_COMPUTER_USE_20261113_V1.md` reports an earlier eight-PR pilot: PEP 585 developer-change coverage 197/525 and 52 wrong changes in its strict family arm; utcnow 140/410 and 65 wrong changes in the assumed-import arm. The latter assumes imports resolve, and neither arm runs the projects' tests. These are historical producer measurements on a small selected sample, not a new independent benchmark or universal success rate. That holdout has now been inspected and should not be reused as a final blind test.

## This change

An example can remove `import random` incidentally while showing `cgi.escape` replaced with `html.escape`. Previously, applying that rewrite to another file could also delete `random` merely because the example removed it. Importing a module can have side effects or expose an API to other modules even when no local AST name uses it. The editor now requires the specific successfully rewritten target place to have read the name before it considers removing that import. An intentionally failed probe does not authorize removal. Existing safeguards still apply. This reduces one failure mode; it cannot prove a removal safe when a rewritten name is exported, used dynamically, or needed for import side effects.

The standalone teaching pipeline also failed on the current package/absolute-import fallback wrapper. It now carries the sibling dependency for that form; the bundle was re-taught, not hand edited. `teach_actions_v1.py --check` reproduced the 11-skill bundle.

An initial broader run returned **182 passed, 1 failed**: `test_what_was_not_taught_is_still_refused` for a compound rename-and-delete request. The target became JSON despite the request returning failure. A trace showed that the legacy compound plan bound a semantic-acceptance compiler's report output to the target file and ran it before a later step failed. The compound execution preflight now refuses before running any step if a non-source-editing capability's concrete output points to an existing named task file, unless that capability's uniquely identifiable clause explicitly nominates the file as the output. The original parametrized test now passes; targeted learning, import and front-door tests passed **188/188**. A separate broader route/composition selection returned **61 passed, 9 failed**, both concurrently with the focused set and on a subsequent serial rerun. Baseline attribution has not been established. Full suite and a fresh external transfer benchmark were not run.

This preflight covers the identified rendered-plan path and concrete file outputs only. It relies on the existing heuristic classification of source-editing capabilities and destination parsing; missing capability IDs, dynamic output references, other executors, side effects, and races need separate analysis. A refusal is not a general guarantee of rollback, and these tests do not establish a security boundary.

## What current research suggests, not guarantees

- AgentCL's controlled related streams and independent held-out tasks show that memory may not transfer and can interfere; compare memory-off with memory-on, rather than treating a stored skill as a success ([AgentCL](https://arxiv.org/html/2606.02461)).
- SkillLearnBench reports gains over no skill on its selected skill-dependent tasks, but no approach leads across all tasks and models; skills can overconstrain open-ended tasks ([SkillLearnBench](https://arxiv.org/html/2604.20087v1)). VibeMemBench isolates memory for executable coding tasks and finds retrieval systems often do not beat the matched no-memory baseline in its tested settings ([VibeMemBench](https://arxiv.org/pdf/2609.23570)). These are research results, not guarantees for this repository.
- OSExpert explores and verifies application skills and reports improvement on a limited desktop benchmark, not arbitrary applications ([OSExpert](https://arxiv.org/html/2603.07978v1)). SkillShift-Bench tests changes in web environments and observes degradation under shifts ([SkillShift-Bench](https://arxiv.org/abs/2610.33528)). OSWorld 2.0 reports 20.6% full completion for its best tested configuration under its 500-step protocol, with a different partial score; this is not a current universal leaderboard or an OSWorld 2.1 result ([paper](https://arxiv.org/abs/2606.29537)). The project now recommends the pinned 2.1 release ([repository](https://github.com/xlang-ai/OSWorld-V2)).
- OSGuard evaluates both local action judgments and end-to-end unsafe effects; a good-looking local decision does not prove the whole trajectory safe ([OSGuard](https://arxiv.org/abs/2606.15034)). The same distinction matters for this repository's preflight: test actual file state, not just returned status.
- Public benchmark exposure and flawed tests can mislead: OpenAI's SWE-bench Verified audit reports contamination and recommends caution, not that every benchmark comparison can be attributed to leakage ([audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)).

## Highest-value next steps

1. **Contain effects first.** Investigate the failing refusal test; guarantee write operations are confined to an authorized disposable workspace and reject unsupported compound requests before dispatch. Test full filesystem diffs on both success and refusal, including deletions, symlinks, paths and external sends. Never use an untrusted demonstration or retrieved page as authorization.
2. **Measure one useful real workflow.** Choose a task family and objective independent tests in disposable environments. Freeze new hidden repositories or environments and evaluators before tuning; separate train/development/test by repository and change family. Use reproducible snapshots, least privilege, explicit confirmation for consequential actions, and no secrets.
3. **Compare matched arms.** Same model, tools, time and cost: no memory; raw demonstration retrieval; structured experience with provenance, applicability conditions and checks; optionally a weight-trained/replay arm if resources permit. For each run record first-task performance, held-out transfer, retention after unrelated tasks, incorrect edits/side effects, abstentions, latency and cost. Use multiple independent tasks and seeds, paired comparisons and uncertainty intervals. Audit evaluator shortcuts and publish failures; examples and their target answers must not leak across splits.
4. **Promote only measured improvements.** Keep experiences versioned and revocable; recheck applicability and outcomes in the target environment, and roll back on regressions. Expand to distinct programming languages and pinned desktop/web environments only after reliability on the first family. Re-run old tasks to measure forgetting and interference. Human review remains necessary where verification is incomplete.

These steps can test whether experience makes an agent more capable and cost-effective; they do not solve every possible computer task or establish a path to sentience.
