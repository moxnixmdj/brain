# Retained repair through the fabric — unadmitted trace, 2026-11-02

This is a source trace and producer-run sandbox measurement, not independent verification, admission, proof of global safety, or evidence that the fabric learned a repair. The owner’s larger goals are not reduced to this one slice.

## Actual selected RAW_GOAL route

1. `unified_cognitive_fabric_v1.run(mode='RAW_GOAL')` passes the goal and options to `live_brain_runtime_v1.run(mode='raw_bound')`. `_run_raw_goal_impl` compiles against the live registry and, for the observed non-editing-auditor mismatch, asks `swe_typed_plan_v1` for an admitted editing proposal. In the measured fixture this selects `python.software.repair.apply.verified.v1`.
2. The single selected bound capability becomes an `invoke_verified_bound_capability_adapter` controller action. The kernel calls `verified_bound_capability_execution_adapter_v1.execute`, whose promoted-entry `inspect` reads the bound registry (including snapshot overlay). Current actual verification metadata says `SANDBOX_MEASUREMENT_ONLY__NO_TWO_SPRITE_FALSIFICATION_CLAIMED`; the gate refuses `BOUND_CAPABILITY_INDEPENDENT_VERIFICATION_NOT_EVIDENT` before target repair. `independent_sprite` and a test count alone are not a separate verifier with a run reference.
3. With learning enabled, the fabric records that exact refusal in the ignorance ledger. With learning disabled it does not. The new draft preserves the gap but does not let this particular gate refusal initiate automatic repair, execute a pending improvement-queue drain, or record an R3 retry capsule. This is not a claim that all other refusals or paths are safe.
4. If the independent-evidence gate is satisfied in the future, that by itself still does not establish an execution boundary. Repair runs target tests and generated candidate tests as host subprocesses. The new draft refuses the promoted bound repair executor after inspection and blocks its known local-dispatch, composer and selected raw compound/DAG paths. It does not confine a direct call to the adapter, direct kernel APIs, or other repair/test-running adapters.
5. The existing frozen action template contains no `retained_learning` binding. The promoted adapter previously rendered and dropped a supplied retention setting without telling the caller. `prepare` now refuses that mismatch after the real inspection gate. An unadmitted candidate action in `RETAINED_REPAIR_ACTION_TEMPLATE_CANDIDATE_20261102.json` adds a retention placeholder, and local tests with mocked inspection exercise exact propagation only as a preparation shape, with `execution_authority=False`. No registry template was changed. The existing template declares optional arguments, but the shared renderer treats them as mandatory; the repair-specific preparation path now prunes only missing directly bound optional args from a copy, validates an explicitly supplied retention enabled flag, and leaves required/mismatched placeholders fail-closed. The separate shared kernel renderer still has the old behavior. RAW_GOAL also explicitly refuses a supplied `retained_learning` setting rather than silently ignoring it. The fabric's BOUND_CAPABILITY mode and `LIVE_CAPABILITY` bound invoker refuse `learn=False` together with retention enabled, and reject configurations placed outside the actual capability inputs. These protections do not implement retained learning through RAW_GOAL.

The two gates are distinct: an actual separate verifier and accepted action contract are needed for admission, and a qualified carrier plus safe effect application are needed before running untrusted tests. No certificate or verified registry flag was created here. The general promoted-capability `inspect` predicate also accepts certain booleans, a verifier-name string, or a mission-anchored receipt; those encodings do not by themselves prove a distinct person actually verified this repair. The receipt-projection path is a separate mechanism whose source checks fields including a declared OIDC issuer and repository; this trace does not establish cryptographic verification of those fields or authorize reusing a producer's hash as independent evidence. Follow the repository's real admission and independent-verifier requirements rather than attempting to satisfy a predicate with self-authored metadata.
