# Computer learner inside the existing namespace launcher — 2026-11-02

## Result and scope

This is a **local research measurement, not admission or independent verification**. `isolated_computer_learning_probe_20261102.py` runs the current worktree's Python runtime and SWE-kernel source snapshot in `zero_ambient_namespace_launcher_v1.run_confined`, with synthetic files and only real `/usr/bin/gzip` on the learner's PATH. No user file is passed in and no output is published to the user filesystem. The snapshot includes only Python source, not Git metadata, user state, or fixtures. The worker is trusted experimental code, not an adversarial third-party program.

The teaching worker solved one gzip goal. Separate fresh cold and warm workers were then given the same different filename and content. The warm worker received a bounded, explicit bundle of JSON memory files from the teaching worker via the broker; cold started with none. The warm worker reported `PASS__RECALLED_AND_REVERIFIED` and `from_memory=true`; teaching and cold reported single-action discovery and `from_memory=false`. On the host, complete decompression of each returned gzip matched the corresponding synthetic source exactly. This is reuse within one narrow gzip family, not a new type of computer task or front-door execution. Timings from one run do not establish a speedup.

**Cold is not a learning-disabled control.** `discover` performs exploration and writes learning state even with an empty starting store. A real off switch must cover its positive and negative recall/retention and fingerprint cache, the search path (`transfer_learning_v1.drive` persists successful search outcomes even when `use_transfer=False`), and other persistent/in-memory caches, including help text. Decide explicitly whether within-run model learning is also to be disabled; merely clearing a store or disabling transfer is not sufficient. None of this has been implemented or claimed here.

## Controls and observed behavior

- The worker reported denial of reads/writes of a host-only sentinel, denial of writing its `/input` request and `/usr`, absence of a fake parent environment secret, and failure to connect to the host's loopback listener. The parent independently checked the sentinel and request bytes remained unchanged and observed no connection at its listener. A host-side connection to that listener succeeded first. Read denial, environment absence, and the other worker-reported fields remain observations from the trusted worker, not independent external proof.
- The worker reported that a valid gzip containing incorrect bytes was rejected as `OPEN__OUTPUT_CONTENT_MISMATCH`, a missing input was refused, and an existing output was preserved. These negative controls run inside the same launcher; their observations are worker reports.
- A separate worker forked a child which called `setsid()` and attempted a delayed broker message after the wall-clock limit. The launcher returned `WALLCLOCK_LIMIT_EXCEEDED`, return code -9, and only the initial `READY` message. This is one process-tree test, not a general proof of cleanup.
- The existing launcher suite covers TCP/abstract-socket separation, failed mount, memory and process limits, inherited-FD closure, ignored stdout/stderr, broker overflow, and parent identity. `python3 -m unittest -v test_isolated_computer_learning_probe_20261102 canonical.tests.test_zero_ambient_namespace_launcher_v1`: **6 tests passed** (one new end-to-end probe plus five existing launcher tests).

## Why this does not yet justify production wiring

The launcher uses Linux user, mount, network, PID, IPC and UTS namespaces, a chroot, capability dropping and `no_new_privs`, a read-only `/input` and host `/usr`, private tmpfs and selected rlimits. It returns material only on a bounded inherited broker socket. A consumer must reject timeouts, overflow, malformed messages, nonzero return codes and unverified artifacts; `CHILD_EXITED` alone is not success. The probe does not publish the returned artifact and does not build a production consumer.

The boundary still exposes host `/usr` for reading and shares the host kernel; it lacks a seccomp policy and aggregate cgroup CPU/memory/PID accounting. The process and memory rlimits are not equivalent to aggregate cgroup limits; process limits also interact with the host UID. There is no demonstrated protection against kernel exploitation or every process/FD/channel attack, no trusted production broker protocol or safe untrusted memory import, and no independent security review. Availability depends on user namespaces and required host tools; there is no unrestricted fallback in this probe. Exposing host `/usr` also means a disclosure policy must account for anything sensitive placed there.

The unified `RAW_GOAL` route still does not invoke this learner in the measured compression scenario. At the time of the original probe, `live_brain_route_admission_v1._serve_by_acting`, the `composer_route_v1` fallback, and the learning fallback called the learner directly without this launcher. A later **unadmitted local draft** refuses those fallback calls and several related automatic execution paths; see `COMPUTER_EXECUTION_BOUNDARY_DRAFT_20261102.md`. This does not secure every route or direct API, and it suspends existing fallback behavior rather than supplying a replacement. Avoid running remaining paths with untrusted programs or valuable files.

The existing action-intent draft remains unadmitted, and the independent-verification requirement has not been satisfied. Wiring around either gate or treating this producer's probe as certification would be contrary to repository governance. Next work needs a threat model, reviewed resource/isolation and broker policy, a genuine learning-off control, and an independently admitted route before testing end-to-end front-door execution and safe publication.
