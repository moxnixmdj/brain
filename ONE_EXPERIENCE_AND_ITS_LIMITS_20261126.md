# What one repair taught Brain — and what it did not

**2026-11-26 · `arena/92aa8a9e-brain` · base `c5d59dd0` · §6 not met.** Local experiments and an audit of separately identified historical runs. No new leaderboard result, capability promotion or merge.

**Follow-up:** The [witnessed-route experiments](WITNESSED_ROUTES_AND_HARD_TASKS_20261126.md) now include four upstream source-verifier grades, a staged positive control, a real-browser effect check and a dialogue failure. Sections 1–3 below retain the original Click study and its earlier worker versions; the [audit update](#the-15-mechanisms-and-nine-prs-what-reached-an-execution) separates those from what was run next.

One successful repair was enough to **originate an edit** without reading a receiver's tests. It was not enough to know **whether to make that edit**. On the original Click parent, replay fixed the failing requirement and preserved the native suite. On four preselected nearby versions it fixed four transplanted failures but broke one transplanted pass **and three native passes on every version**. The generalized rewrite did no better than exact replay.

The useful new result is a way to catch some of this *before* grading. On two revisions, following an advertised CLI subcommand rather than visiting four root help pages found a caller whose output changed. Removing the edit restored the original bytes. A later process can now refuse that edit **if the goal requires preserving those bytes**. It cannot infer that preservation is the right goal. On two hard Ansible tasks we did not even acquire a failing, requirement-specific observation or emit a patch. Those are the two places to work next, not the speed of skill lookup.

## 1. What persisted, and what counts as learning

The runtime in these experiments is Brain's own program. It computes candidate edits, runs them and compares observations. There was no trained model update, external model inference or downloaded answer in the solve loop. Acquisition of public source, tool installation, literature research and evaluation were separate host/build activities. Zero inference fees does **not** mean zero CPU, developer time or CI cost. This is not evidence for a general learned neural model or a proof that all code in the repository is free of domain priors.

The §2 boundary is operational: keep **mechanisms in code** and **fallible, versioned knowledge outside it**. Retain a small rewrite, its teacher, conditions and the check that can invalidate it. A teacher-checked pattern is a *proposal*; a triggered call is *reach*; an observed difference is an *effect*. None of those supplies a *requirement*. A transfer claim needs a distinct task, a failed requirement on its base, a flip of that requirement, preservation of working behavior, and a matched run without the learned object. Prefer verified successes or fewer evaluations at the same success; report regressions, abstentions and costs too.

| §3 claim | Verdict on this evidence |
|---|---|
| One experience can change the next run without retraining | **Yes, narrowly.** On Click `~4`, deleting just the teacher entry from a copy of the store, reopening it and probing the same 17 files changed the file-hit counts from **0/1/1 to 0/0/0** (empty/exact/generalized). |
| An experience can encode more than a path, constant or raw transcript | **Yes as a mechanism.** The rewrite binds identifiers in nested statement windows; a rename-and-rehost test distinguishes it from exact replay. The real receivers did **not** establish a generalized repair advantage. |
| Observing a counterexample teaches something durable | **Yes, conditionally.** Two stored vetoes matched two distinct candidate hashes under the exact preservation obligation. Deleting one and reopening left **false/true** instead of **true/true**. Changing the obligation did not trigger the veto. This affected a decision, not a task reward. |
| A successful advanced coding action implies permanent mastery anywhere | **False as a guarantee.** Even a near-identical site in the same library can be called under a different contract. A new environment may lack both the site and a way to determine the desired result. |
| The strongest coding and arbitrary computer-use capabilities are already unified and working | **Not established.** The corrected cold entry point emits actions. Emitting an action, having an indexed engine or replaying a long simulated plan is not finishing a hard task. |

## 2. One teacher, three treatments, separate grades

**Teacher.** The input was the **generated** candidate for `pallets/click@05f6fd0`, not its human fix. It had cost **38 candidate evaluations / 36.0 s** and a separate historical replay of **116 passing tests**. From the pinned parent file and candidate, Brain extracted the guarded `Argument.get_help_record` edit in **0.2525 s**. A whole-module representation had carried the enclosing file; the new learner finds the changed statement window, keeps necessary sibling bindings, checks for unbound identifiers, and requires application on the teacher to reproduce the changed **AST**. If similarly shaped sites make the first match wrong, it refuses. This is not a semantic-equivalence proof. Nor is abstraction necessarily compression: **184 bytes** of schema vs **180** for the exact window pair; **1,313** bytes for the persistent record. Comparing to two *whole files* would exaggerate the saving.

**Arms.** Empty store; exact old/new window from that teacher (`raw_traces`); generalized window from the same teacher. Same sorted Python product files, at most one proposal/file/arm; freeze the first hit **without a verifier**. Calibration on the original parent searched `core.py` only. The Ansible and older Click controls came first. The [prospective protocol](canonical/verification/RECEIVER_CONTRAST_PROTOCOL_20261126.md) fixed the next offsets `~1, ~16, ~64` and the Typer release before opening them. After lexical probes missed the affected method, we fixed the two midpoints and the directed policy **before** opening those trees or grading. `~N` is first-parent distance from **`f25f697a`**, not N independent tasks. None were replaced.

**What the pre-grade probe did.** In disposable offline rooms containing staged product and example Python sources, the lexical policy called four root `--help` entry points. The directed policy used names from the changed definition to rank decorated callers, asked for root help, and followed one name actually advertised under `Commands:`. It used the unchanged checkout to select the request sequence once and repeated it on both edits. This is a matched no-edit comparator, not an empty-store learner discovering the sequence unaided. The implementation is CLI-specific; it is not a general license to execute unknown programs.

On `~4` and `~32`, lexical had **0/4** requests reaching the edited method; directed had **1/4**. Request three was the receiver's own `repo clone --help`. Both sides exited 0; `Argument.get_help_record` ran **four times**; stdout went from **437 B** (`9054a2ddf634…`) to **475 B** (`70f537a4cd4d…`); stderr stayed empty. The whole three-arm diagnostic took **4.279 vs 4.017 s** on `~4`, **4.373 vs 3.933 s** on `~32` (lexical vs directed). Budget: at most four actual requests per arm/policy, 5 s/command; equal request counts do not equalize host-side example parsing cost. Click had ten eligible examples. No reach is **unmeasured**, not preservation.

**What the evaluator did.** Pre-grade records were frozen at `90c9997f` (manifest `413b5881f9971f282cb6f383dd8ec82c703fc7523f4f590498d2f987beb2d43e`). Each arm got a fresh native default suite, then, in a different copy, *only* the teacher's checked test file. Both use real pytest case identities. The two policies at each midpoint had the **same product manifest and the same candidate path/digest within each arm**; exact and generalized were graded separately. The native regressions concerned metavar formatting and wrapping long command names/options. The transplanted regression concerned an all-undocumented-arguments section. A net gain of three tests would have hidden it. This is a compatibility study, not five novel user requests or an unseen benchmark.

The initial older-control native run lacked Click distribution metadata. On `~32`/`~64`, pytest 9.2.0 failed collection on an upstream parametrize deprecation (exit 2); **not a candidate failure or pass**. We kept those runs, installed the exact receiver package and used the matched project lock for the two separate regrades (pytest 9.0.2 plus four hash-pinned dependencies). The table uses completed runs. In the five-offset study native checks took **5.631–7.044 s**, transplanted checks **0.466–0.567 s**, 120 s cap/run. Native defaults skip/deselect cases, including the stress suite; not all possible inputs. No policy or patch was fitted to these grades.

**What was saved.** A post-grade no-edit/edit/no-edit repeat in fresh rooms reproduced **437 → 475 → 437** and the hashes on both midpoints and both edits. An external refutation records the candidate digest, receiver and example manifests, driver/interpreter, request, preservation obligation, observed hashes and calls. No positive law was admitted. The deletion control in §1 changes just the recalled proposal or scoped veto, not the original files. A new caller, requirement, or environment needs a fresh witness.

### The 15 mechanisms and nine PRs: what reached an execution

All **15** nominated source files exist. The [organ-by-organ audit](canonical/verification/WITNESSED_ROUTES_AUDIT_20261126.md) gives the paths, required inputs, call sites and evidence limits. They do not form one pipeline by virtue of being in the same checkout:

Some of their *drivers* use a fix commit's tests. Those drivers stayed out of the producer. Reaching `boolean` in a passing test didn't name its missing behavior.
- **Originating an edit:** history-template instantiation, witnessed fold/propose and operator generalization each cover a limited edit family. This establishes a previously missing execution path, not a hard-task repair.
- **Checking and remembering:** causal-dataflow frames suggest where to edit; read-set interventions can test a dependency; the input-dependency gate can reject dropped inputs; the lesson pipeline rechecks a proposed application. ## 6. Minimal plan, rejection criteria and reproduction

**One loop:** read the goal and a cheap local inventory → retrieve a *conditional proposal* → identify a caller or state that would distinguish it from no action → acquire a **permitted source of intent** (public example with expected result, an explicit constraint, or a trusted native check) → in a disposable copy, reproduce the failure, apply the edit and check both the flip and protected controls → checkpoint or abstain → store the smallest reprobeable change in what Brain knows. For a GUI the analogue of a passing test is an externally read-back state predicate; before resuming, re-read the affected state rather than trusting a saved plan. That last extension is a design, not an OSWorld result.

**What is unknown?** Here it is not “what does `get_help_record` return?”; we can execute that. It is “should this caller show an arguments section when *none* of its arguments have documentation?” Both policies fit the fact that the teacher succeeded. The cheapest useful next observation is one on which the policies disagree *and for which intent can be read independently of the edit*. Scan enough names and dependencies to find that observation; fetch only information that can change the decision. Delay permanent storage of raw inputs, traces, exploratory mutations and unlabelled output changes. Keep a goal-relevant, surprising, reproducible procedure as a hypothesis; spend the more expensive transfer, preservation and compression checks before promoting it. Version or remove it when its evidence changes. This is a decision rule to test, not a claim of global optimality.

**Next decisive trial:** freeze the engine, unrelated teacher, receiver selection, data permissions and equal wall/action budgets *before* opening new tasks. Use an authorized Docker runner for the selected hard slice; keep producer and grader isolated. Run matched empty/exact/generalized and one-entry-deleted controls on genuinely different tasks, including unsupported languages. The already studied positions are engineering repeats, not fresh blindness. In parallel, on a fresh receiver with a public requirement, compare first failing file vs directed acquisition at equal execution **and** acquisition cost. Count: (1) base failures tied to the requirement and reached caller, (2) frozen nonempty patches applied on a clean base, (3) external rewards, lost passes and surviving obligations, (4) verified gain or time/evaluations saved specifically because one stored rule was present. Count missing setup and refusals separately without dropping them from the selection. For OSWorld, provision the matching release, VM, task assets and evaluator first; bound actions/time and record strict and partial completion, including mid-task drift and restart. No benchmark outputs go into the next producer.

**What would change the verdict?** A learned arm that solves a distinct task under its own judge while the matched no-memory arm does not, whose advantage disappears on deleting that one lesson, with no regressions, is evidence of transfer on *that task*. Repetition on independent tasks would support a broader claim. If directed acquisition finds only more calls but no labelled failures, reject it as the current bottleneck fix. If a labelled failing call is acquired but the correct patch is never proposed, move the bottleneck to generation; if it is proposed and discarded, investigate ranking/verification. Don't add a new store, extra parallel forks, a universal cross-language rewrite, or a library of hand-coded fixes for the exposed cases. None produces the missing requirement. Don't learn every file or bake verifier knowledge into weights. Keep the exact-window control: here it was at least as useful as the larger abstraction.
