# Repair isolation and effect receipts: review design

**Status: design only; not approved, implemented, qualified or independently verified.**
Date: 2026-11-24. No execution authority, capability promotion, score claim or cloud authorization follows from this document.

## 1. Why the repair door remains closed

`canonical/runtime/confinement_v1.py` clones a repository and starts an ordinary host subprocess. A controlled temporary-repository test wrote a sibling sentinel outside the clone while its result still reported `host_untouched=True` and `verified=True`; see `canonical/tests/test_confined_repair_execution_adapter_v1.py`. Git status equality is not an isolation boundary and misses writes outside the repository, as well as some changes within it. The candidate repair wiring was reverted. The pre-existing `live_brain_route_admission_v1` dispatch also uses this clone carrier; do not treat it as protection from untrusted code. Disabling or replacing that existing route is a separate change requiring its own impact review.

`receipt_sha256` in that carrier identifies the pre-execution basis; its separately computed result digest is not passed through by the existing dispatch. Neither a 64-character identifier nor a worker-supplied hash verifies emitted bytes. The SWE adapter currently extracts a returned patch or worktree diff, not an effect verified under this design. No 0.0% leak rate is established by these observations.

## 2. Existing OS-boundary work and measured availability

The repository already has `zero_ambient_namespace_launcher_v1.py`, `worker_syscall_allowlist_v1.py`, and `brokered_workspace_execution_v1.py`. The namespace launcher uses user/mount/network/PID/IPC/UTS namespaces, a changed root, restricted mounts, a syscall filter, and a broker channel. The broker explicitly reports `carrier_qualified=False`. `REPAIR_INDEPENDENT_REVIEW_REQUEST_20261102.md` describes outstanding review and qualification requirements; its later addendum notes that filtering exists but has not been independently reviewed. These are candidates, not admission evidence. Do not route untrusted repair through them merely because they exist.

On this sandbox, 2026-11-24, `unshare --user --map-root-user --mount --net --pid --fork --ipc --uts /usr/bin/true` exited 0 and `namespace_broker_available()` returned True. This is only a prerequisite probe: it does not prove confinement, cleanup, receipt correctness or suitability for SWE repair. `bwrap`, Docker, Podman and nsjail were not found. The namespace candidate exposes host `/usr` and related libraries read-only and uses the host kernel; a working namespace or a container is not a VM boundary and cannot guarantee immunity to kernel vulnerabilities.

## 3. Threat model and candidate boundary

The attacker controls the task repository, test code, worker output and candidate patch, including filenames, symlinks, subprocesses and attempt timing. They must not read credentials or other ambient host data, write outside the allocated scratch filesystem, reach host services or the network, influence the trusted monitor, forge a receipt, leave descendants alive, or cause unbounded resource consumption. The host kernel, isolation runtime, trusted monitor and verifier are part of the trusted computing base; compromise of that base is not ruled out. State explicitly which attacks and runtime dependencies are in scope before any approval.

Preferred evaluation is on a dedicated, disposable, unprivileged Linux machine with no credentials or sensitive mounts. A hardened namespace/container boundary with a pinned minimal runtime is a candidate **only after** review and observed qualification; merely running Docker, unshare or bubblewrap does not qualify it. For a local gate, use such a separately reviewed boundary on the local environment if its prerequisites are available; if they are not, the local gate remains blocked. A VM is not a substitute for the required local gate and no external benchmark smoke test or cloud spending is authorized by this document.

Candidate design, subject to independent review:

1. A trusted parent prepares a bounded, sanitized snapshot of the task repository at the declared base commit. Treat all inputs as data; do not use host `.git` hooks, inherited descriptors, credentials, caches, sockets or environment secrets. Put the exact approved runtime and executable code in a separate pinned, minimal, read-only image. Review package, dependency and task compatibility rather than binding the host `/usr` by default.
2. Create isolated user, mount, PID, IPC, UTS and network namespaces, a private mount tree and filesystem root, private scratch and a read-only input. Remove capabilities, set no-new-privileges, apply a reviewed seccomp policy, close every non-allowlisted descriptor, and enforce network denial. Do not mount the host Docker socket, home, source checkout, or host-sensitive paths. Workers get only the approved input, runtime, private scratch and a bounded output channel. All setup steps must succeed before any task code runs; unsupported architecture, missing primitives or failure means refusal with no fallback.
3. Apply aggregate CPU, wall-clock, memory, PID, output and storage limits to the whole worker tree, not just one process. A trusted supervisor must be able to kill and reap all descendants on timeout, crash and cancellation, and observe quiescence before harvesting effects. Treat leaked descendants or unverifiable cleanup as failure. An external privileged supervisor/cgroup delegation may be necessary; availability must be explicitly measured rather than assumed.
4. No automatic adoption to a host worktree. A trusted collector outside the workload takes a stable snapshot of declared effects after quiescence; publication is separate, explicit, reviewed and constrained to the approved output. A private channel carries untrusted bytes, not authority.

The current broker's writable `/work` and output channel might inform an implementation, but exact snapshot/patch semantics, trusted runtime, all lifecycle guarantees and independent qualification are not established for this use. Do not change `carrier_qualified`, declaration rows, protected paths or truth counters as a shortcut.

## 4. Effect receipt and verification protocol

The **trusted collector**, not the worker, must enumerate the explicitly declared relative effect paths against a stable, bounded snapshot after all worker processes are gone. Reject absolute paths, `..`, NUL, duplicate/ambiguous paths, symlinks and hard-link or special-file escapes, non-regular files unless specifically specified, traversal races, excessive output and effects outside policy. Resolve paths with directory-relative, no-follow operations or an independently reviewed equivalent. Hash the exact bytes read once and make those same immutable bytes available to the verifier; do not re-open a mutable worker path after hashing. Fail on unstable reads or unverifiable cleanup.

A versioned canonical receipt should bind at least: run ID; base commit and input snapshot digest; exact runner/runtime and policy digests; isolation and resource-policy identifiers; declared normalized effect paths; for each effect its byte length and SHA-256 over its actual bytes; exit/timeout and cleanup outcomes; and the collector identity/version. Canonical serialization and hashing rules must be specified and tested. The trusted verifier independently parses the receipt, checks all required fields and allowed policy against reviewed expectations, recomputes every output hash over the exact immutable bytes to be consumed, and refuses if any field, path, length or digest differs. A receipt hash alone is an integrity identifier, not authentication, independent verification, proof of host safety, proof of task success or authority to publish. If authenticity or independent provenance is needed, use a separately managed verifier/attestation mechanism; a worker or producer must not self-certify.

The benchmark patch should be a declared effect consisting of the **exact patch bytes** eventually emitted. Hash those exact bytes; validate encoding, supported relative paths, size, applicability and task/base binding before constructing the SWE-bench prediction. A file-hash manifest alone does not bind a patch unless the verifier also binds the exact patch bytes and its relationship to the declared effects. The harness, not this receipt, decides whether a repair solves the task.

## 5. Pre-registered qualification checklist

Run benign characterization locally first; any adversarial or resource-exhaustion probes require a disposable, non-sensitive environment and explicit resource controls. Independent reviewer must witness or reproduce the exact candidate artifact and configuration on the target OS/kernel. Record distinct verifier identity, exact commit and dirty-tree hashes, runtime/image and policy hashes, environment, commands, numeric outcomes and a distinct run reference; failures and skips stay visible.

- **Setup fail closed:** namespace/mount/root transition, filter, limits, broker, snapshot and cleanup failures must prevent workload execution; no clone-only or host fallback.
- **Filesystem and descriptors:** read/write attempts against sibling sentinels, host paths, `/proc`, inherited descriptors, nested mounts, symlinks and hard links must not access host material. Include benign real project execution so a locked-down but unusable carrier is not mistaken for success.
- **Network and process:** host network and services inaccessible; host PIDs and process manipulation blocked; timeout/crash/cancel kills all descendants and collector observes quiescence.
- **Aggregate limits:** controlled PID, memory, disk, CPU and output tests fail within approved limits, without destabilizing the test host. Tests not safely runnable are a blocker, not a pass.
- **Effects:** missing, undeclared, duplicated, escaping, changing, special and oversized effects refuse; mutate an effect, patch, manifest, run ID, base or policy and require verification failure; a genuine declared effect must verify against its exact consumed bytes.
- **Front door:** independent evidence remains first; only reviewed declaration and bound effects can reach a qualified carrier; setup failure, timeout, invalid or unverified receipt and all escaping paths preserve the applicable refusal and never hit the host executor. Exercise real adapter and `open_model().solve()` envelope, not only mocks.
- **Patch gate:** on five identified local instances, emit at least one non-empty patch whose exact bytes match a verified trusted-collector receipt. Retain per-instance refusal and receipt evidence without answer leakage. Synthetic fixtures must be described as synthetic; this is not a SWE-bench score.

## 6. Decision and order of work

1. Review this threat model and compare candidate carrier approaches and their exact trusted computing base. Independently review/qualify the chosen implementation before enabling any route.
2. Implement and test isolation, bounded collection and receipt verification without changing the existing refusal. Obtain independent review and re-run the registered negative and legitimate-work tests against exact bytes.
3. Only then propose Phase A wiring. T1–T7, real front-door evidence and a no-host-fallback review must pass. Separately review any Phase B/C changes; the current wrapper cannot satisfy the receipt-backed patch gate.
4. Run the five-instance local gate and require at least one verified non-empty patch. Only a passing gate plus owner approval permits considering the external SWE-bench Verified smoke test. No claim is made that this sequence will yield a patch or a benchmark score.
