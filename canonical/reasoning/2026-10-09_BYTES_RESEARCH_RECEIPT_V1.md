## Core optimization object

### 1. Conditional terminal bytes

For an already-owned Brain substrate S and required capability set C:

```
B*_R(C | S) = minimum resource-feasible unique persistent description
              whose complete dependency closure realizes C
```

A practical decomposition is:

```
B_terminal =
    B_shared_substrate
  + B_router_and_configuration
  + sum(B_true_capability_residuals)
```

subject to:
- every required capability >= its accepted frontier bar;
- donor deletion;
- protected held-out qualification;
- interference/non-regression constraints;
- runtime latency limits;
- memory limits;
- compute limits;
- reliability limits;
- hard $0 incremental spend where mission-applicable.

Raw Kolmogorov-smallest description is not the correct engineering target because a tiny program may regenerate a huge capability with absurd runtime. Bytes uses a resource-bounded description objective.

### 2. Marginal vs terminal bytes

Do not confuse:

```
Delta_B_i = B(C_1..C_i) - B(C_1..C_(i-1))
```

with:

```
B_terminal = B(C_1..C_n)
```

A capability may have near-zero marginal bytes because an already-owned shared substrate contains its machinery. That does NOT make the shared substrate free.

### 3. Content-addressed unique bytes

Logical path size overcounts duplicated content.

The storage objective must count each identical content blob once before higher-level factoring.

### 4. Execution / verification / proof / JIT separation

Track at least:

```
B_exec   = persistent bytes required to perform capability
B_verify = persistent online verifier bytes required for autonomous correctness
B_proof  = receipts / experiment logs / historical evidence
B_JIT    = transient task knowledge
```

B_proof is important governance state but is not itself cognition.
B_JIT is not permanent capability storage.
Do not add either to B_exec merely because they live nearby in the repository.

### 5. Complete dependency closure

A nominally tiny artifact is not tiny when it requires a large hidden base.

Examples:
- a 2 MB adapter requiring a 40 GB base is not a 2 MB capability;
- a small Python wrapper depending on a capability-bearing CAS must count the CAS closure unless the CAS is classified as shared already-owned substrate;
- masks, indices, routers, decoders, tables, constants, prompts, and configuration all carry information and must be accounted for when load-bearing.

## Capability-bearing dependency test

A dependency is not free merely because it is external or labelled "runtime".

For dependency D and target capability C, ask:

1. Remove or replace D with a generic substrate preserving interfaces.
2. Does the Brain-owned configuration still provide essentially the same target capability?
3. If NO, D is capability-bearing for that route and belongs in the dependency closure unless it is already counted once as shared owned substrate.
4. If YES, D may be generic substrate, but the claim must remain within the tested scope.

This extends the existing external-capability-provider test to byte accounting.

## Global mechanism-cover formulation

Brain already decomposes behavior into atomic causal leaves.

For each candidate mechanism m_j record:
- atomic behaviors covered;
- complete dependency closure;
- unique compressed bytes;
- latency;
- peak memory;
- compute;
- reliability;
- verifier;
- ownership status;
- compatibility constraints.

Then solve a minimum-weight mechanism-cover / hypergraph selection problem:

```
minimize unique dependency-closure bytes
subject to every required atomic behavior having a verified valid route
```

Dependencies shared across capabilities are counted once.

For a finite enumerated mechanism library, exact branch-and-bound / MILP / exhaustive optimization may certify the optimum within that known mechanism universe. Heuristics may propose candidates but should not certify global minimality.

Absolute universal minimum description length is not computable in general. Claims must therefore be phrased as:
- exact optimum over a finite declared candidate universe; or
- best verified upper bound with explicit lower-bound/gap evidence.

## Elicit-before-teach

Working research distinction:

- ELICITATION: required behavior already exists in an owned shared substrate; a small durable key/configuration exposes it.
- TEACHING: genuinely new learned information must be added.

Recent Excess Description Length (EDL) research is useful as a SEARCH SIGNAL for distinguishing these regimes.

Important correction:
EDL is NOT a proof or lower bound on deployed capsule byte size. It estimates generalizable information acquired during learning, not the minimum runtime dependency closure.

## Counterexample-guided capability compression

For residual behaviors that genuinely require teaching or donor harvesting:

1. attempt with current smallest candidate;
2. find earliest/first irreducible causal failure;
3. add only mechanism needed to close that witness;
4. rerun;
5. generate independent new counterexample;
6. recursively re-minimize all retained bytes.

Formal sketch:

```
R_(t+1) = argmin_R |closure(R)|
          subject to R passing all admitted witnesses W_(<=t)
```

Qualification examples used to select/prune/tune remain contaminated and cannot serve as final proof.

## Shared factoring

Independent capsule minimization is not globally optimal.

Seek:


rather than the sum of separately minimized capsules.
