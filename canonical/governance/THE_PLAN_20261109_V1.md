# The plan

Written after the loop was demonstrated, not before it. Every claim below has a receipt in
this repository.

## What was proven today

A complete computer-use loop, with every component already in this repo and none of it
written for this round:

    browser_launch_v1.sh            -> vendored Chromium, DevTools on :9222
    astra_hidden_visual_executor.py -> Page.captureScreenshot -> 10861-byte PNG
    the model (this session)        -> read the image, chose the point (157, 162)
    Browser.click                   -> Input.dispatchMouseEvent (press + release)
    Page.captureScreenshot          -> 9877-byte PNG, and the heading reads AFTER

Receipts: `canonical/evaluation/the_loop/step1_before.png`, `step2_after.png`.

The gate held while this happened: `Runtime.evaluate` returns `CDP_METHOD_FORBIDDEN`.
The loop is vision and pointer only. It cannot reach through the page with JavaScript, and
`DOM.`, `Accessibility.`, `CSS.` are blocked wholesale.

## What this changes about the plan

It removes the assumption that computer use needs to be built. It needs to be JOINED. The
parts exist in three places that never spoke to each other:

    model      <- r63 socket (model_proposes_v1)
    gate       <- r60/r61 (operation and shape verification)
    eyes/hands <- astra_hidden_visual_executor (CDP, vision-only allowlist)

## The plan, in order, with the cost of each step

### Phase 0 -- done, today
The loop, demonstrated end to end, twice, with images.

### Phase 1 -- one function: `act(goal)`
    screenshot -> model proposes {action, x, y, because} -> gate checks the action against
    the allowlist -> execute -> screenshot -> model verifies the goal is met or picks again

Cost: one module. The protocol already exists in `model_proposes_v1`; it needs a second
action type (`gui_click`, `gui_type`) and a loop with a step budget. The verify step is a
model reading two images and answering one question: did the stated change occur.

Failure honesty: every iteration records the screenshot hash, the proposed action, the
coordinates, and the verifier's answer. A loop that runs out of steps REFUSES; it never
returns the last thing it did as success.

### Phase 2 -- make it learn
Every successful trajectory is already in the shape `compile_and_qualify_skill` accepts:
an ordered list of actions with a postcondition. Store it. Then:

    screen hash matches a taught trajectory -> replay deterministically, no model, ~milliseconds
    screen is different                     -> fall back to the model loop

This is exactly the thesis, applied where it works: one demonstration, then a permanent,
replayable action sequence that costs nothing to run. It is honest about its boundary -- the
replay is keyed to the screen it was taught on, and it refuses when the screen has moved.

### Phase 3 -- widen the surface
The OSWorld V2.1 adapter family (91 files, `BrainOSWorldAgentV3`) already defines the wider
surface: app operations, web-app operations, guest state, typed-GUI receipts. Connecting
Phase 1 to it is the step from "a browser" to "a computer".

Desktop applications are NOT reachable here: this machine has no display server and no
window manager. That is a hardware boundary, not a design one, and it is the honest scope of
Phases 1-3.

## What the plan deliberately refuses

- **Do not rebuild the CDP client.** `browser_v1.py` records that earlier versions wrote
  their own and it was a mistake. Use `astra_hidden_visual_executor` and
  `osworld_v21_*`.
- **Do not add a vision model to the repo.** The model is in the loop already. Adding a
  second one inside the process would be duplication with no receipt.
- **Do not spend another round on lexical selection.** r63 showed the model answers 8/8
  where the lexical layer answered 4/8. That layer stays as a fast path and a fallback, and
  is otherwise finished work.

## The single number that decides whether the plan is working

Not "how many tasks passed". The number that matters is:

    **fraction of trajectories that replay without a model and still verify**

That is the only measurement that separates learning from doing, and it is the thing the
repo already knows how to measure (r59's wipe test, applied to GUI).

## Honest ceiling, stated up front

Today's proof is a two-element page. OSWorld 2.0's frontier is 20.6% binary on real
workflows, and the strongest models on that benchmark often skip the interface entirely.
The loop being correct does not make the tasks easy. What changes is that the difficulty is
now in grounding, planning and robustness -- problems that are worked on by everyone -- and
no longer in a missing sense or a missing hand.
