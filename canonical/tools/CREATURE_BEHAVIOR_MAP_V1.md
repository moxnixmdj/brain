This is a working research map, not a claim of sentience, terminal success, independent third-party verification, or exhaustive semantic review. Reachability observations are static unless explicitly described as an execution. The current worktree contains uncommitted changes and is not identical to a single recorded Git commit.

## Shared task: real tools, separate processes

`computer_branch_comparison_v1.py` accepts a separately prepared living-branch source snapshot and compares it with the current `computer_env_v1` on the same five known line-count input shapes and a missing-file negative control. It starts fresh processes for teaching and every target, copying the original source-only state separately to each warm target. A Python newline count independently checks each answer. The current arm performs its own discovery/probes; the living arm receives a concrete `wc` demonstration plus a canary. They therefore have **different acquisition interfaces**, and the living computer constructs its own admitted binary path while current discovery is deliberately restricted to `wc`. This is an informative shared task, not a controlled comparison of equal instruction or an arbitrary-computer benchmark. The current result does not always report `from_memory`; the benchmark records whether the query cache was present, not a proven per-result cache hit. `elapsed_ms` includes worker-side imports and restore/discovery but excludes process startup and fixture construction.

One local measurement after the long-path fix, repeated three times: current cold and warm both passed 15/15 positive cases; living cold passed 0/15 and warm 15/15. The living cold arm calls `solve` without teaching; it does not invoke the branch's separate acquisition/search APIs, so it is not a full capable-fallback baseline for that branch. All 12 missing-file controls refused. Median worker times were respectively current cold 18.82 ms, current warm 10.16 ms, living cold 31.99 ms and living warm 38.13 ms. These numbers are for one tiny known task, on one machine, and the mechanisms and safeguards differ. They are not general performance rankings.

In the same disposable historical snapshot, 17 existing branch tests covering chunking, drift, impasses, practice and memory passed. Three existing table-induction tests also passed in 16.70 seconds; their first test checks 20 held-out generated tables in each of 12 known families. The induction receives one demonstration **and may query an oracle up to 24 times**, so this is active learning, not demonstration-only one-shot learning. The families and generators are authored and known, not a blind open-world assessment. An initial selection also included six policy tests that errored during setup because the partial snapshot did not contain their historical repository fixtures; those six were not evaluated and should not be counted as passing.

The initial comparison exposed a long-path failure in the current query path: `wc` prints both the count and the filename, and the 64-byte output bound incorrectly included the filename. The change strips only the exact filename passed to a single-stage command before applying the existing one-value bound. A real-`wc` regression covers a long filename containing spaces. The initial long-name case failed for current, while the post-fix case passed.

## Further branch comparisons

`diagnose_branch_comparison_v1.py` runs the branch-only diagnose-then-repair path at `1674df08ad660eb5011cfcda5589f227218caa6a` on the same six constructed boundary fixtures as the live scoped repair benchmark. In one local run, its full suite gate returned `VERIFIED_PATCH` on 6/6; each diff was independently applied to a disposable copy and passed the finite grid audit. Both the original source and declared tests remained unchanged. The already-correct inclusive negative returned `NOTHING_TO_REPAIR:FAILING_TESTS_PASS` and its unchanged source passed audit. The positive runs ranged from 3.15 to 4.76 seconds, including Python worker startup; these are cold search times, not learned-skill transfer times. The historical runner was explicitly configured with one worker, `review=off`, and `confine=off`; the fixed tests were trusted, and these timings are not directly comparable to live benchmark timings that exclude worker startup. The historical snapshot includes the adapter and its imported runtime files from the same commit, not a complete historical checkout. No claim of universal repair follows.

`test_creature_failure_continuity_v1.py` exercises the actual unified front door in one process, then loads its failure record in a second process. The failure survives restart, but is explicitly marked `ORPHANED_TELEMETRY__NO_REPAIR_OBLIGATION_CREATED`: there is no replay context, no queued repair, and no verified skill. This is evidence of durable failure telemetry, not an autonomous repair or an enduring subjective self.

`living_self_model_probe_v1.py` tests the historical living agent's explicit ignorance records across three processes with snapshot/restore. With no skills, both a line-count goal and a delete-like goal failed closed, made zero shell calls, and appeared as open questions. After restore, teaching only a line-count skill removed **both** questions; after another restore both remained absent. The implementation resolves impasses on any shared token, so the deletion question was incorrectly treated as resolved without being performed or verified. The delete-like goal was never submitted after teaching and no deletion was executed. This is a concrete blocker for using its self-report as a reliable self-model; it is not a test of subjective experience.

`sentient_branch_probe_v1.py` probes the PR #5912 head in two fresh interpreters. A single demonstration generated a path-parameterized archive pattern; a separate unrelated goal containing a path was reported `adaptable: true` even with zero token overlap. This control never executes that unrelated goal. After a new instance was created in a separate process with the same empty disposable root, it had zero learned patterns and zero episodes; the trained instance had one of each. This establishes lack of automatic persistence in the exercised API, not impossibility of an external caller building persistence. The code separately delegates actual goals to a live solver, but the probe does not execute that solver and does not test sentience. A changed `decision_basis` or retrieval result alone is not evidence of subjective experience.

## Safe integration work still needed

A disposable manual control showed that the living branch's `_canary_ok` writes canary files into the agent root: teaching with a preexisting `canary.txt` replaced its contents. Therefore do not directly run this branch against a caller-owned directory or wire it into the live front door without isolating canaries and preserving user files. Its shell's path/admission checks are not a general OS security boundary. Its accepted skill's regex and canary are not an independent oracle for every input.

Historical `66cab357f4b5c58e8e149612b444037de5744b4f:canonical/runtime/bound_capabilities/real_swe_execution_v1.py` contains parallel repair, candidate ranking and persistent caches. A prior disposable control found that its candidate/test cache key did not change when an imported sibling changed a test outcome; an expired TTL entry was still returned. This does not demonstrate failure of that branch's separate full test gate. Full end-to-end comparison of that repair branch and real desktop tasks remains open; do not substitute its cached scores for current verification.

Future work: broaden the shared task families and perturbations; compare the branch-only repair paths under a common independent suite and isolated state; establish explicit memory ownership, provenance, invalidation and replay boundaries before integration; measure performance on realistic workloads; and investigate creature-level continuity and self-model behavior separately from claims about subjective experience.

## Reproduction

Prepare a disposable snapshot separately, for example, after fetching the stated commit:

```sh
mkdir -p /tmp/brain-living-snapshot
git archive 207a2b2d7d20fe31c79a2921e7c3dd19a9158001 \
  canonical/runtime/living_agent_v1.py canonical/runtime/living_core_v1.py \
  canonical/runtime/living_discovery_v1.py canonical/runtime/shell_synthesis_v1.py \
  | tar -x -C /tmp/brain-living-snapshot
python3 -m canonical.tools.computer_branch_comparison_v1 --living-source /tmp/brain-living-snapshot
```

The benchmark records SHA-256 digests of the supplied modules and current computer module. Preparing historical source is a manual research step; repository tests run against the current worktree, and do not load Git objects. Run only trusted snapshots: Python imports and shell subprocesses are real, not OS-sandboxed. The benchmark uses temporary directories and does not touch the default memory stores.

For the explicitly named agent, prepare a trusted snapshot containing `canonical/runtime/sentient_computer_agent_v1.py` from the above PR head, then run `python3 -m canonical.tools.sentient_branch_probe_v1 --branch-source /path/to/snapshot`.

For the historical repair comparison, prepare a trusted snapshot of `canonical/runtime` from the stated repair commit and install pytest separately, then run `python3 -m canonical.tools.diagnose_branch_comparison_v1 --branch-source /path/to/snapshot --pytest-path /path/to/pytest/site-packages`. It deliberately uses `confine=off`, so run only its fixed trusted fixtures. `--only disjunction` runs one case.

## Opt-in failure context (in progress)

The `LEARNING_EPISODE` front door now accepts `retain_retry_context: true` for a narrow cold episode with only the basic episode/scope and expansion-limit options, no supplied solver or verification callbacks, and no active skills at admission. Unsupported options and contexts rejected by the existing capsule validator fail before the episode runs. The original problem and solver limit are persisted as a **manual-only generic retry**, with learning disabled. It is a new solve of the problem, not an identical execution trace, and changed environment or concurrent state can change its behavior. Disabling learning does **not** make problem capabilities read-only or safe: a manual replay can have side effects and requires an explicit safety decision. The existing validator rejects sensitive-looking keys, not arbitrary secrets embedded in values; do not retain sensitive problem data without an appropriate storage policy.

A fresh-process test confirms the failed episode's capsule reopens, direct autonomous repair is blocked even without evidence of effects, and an explicitly invoked generic replay of this no-capability fixture leaves the state file unchanged. The normal queued improvement provider is also marked autonomous, so it cannot silently turn manual-only work into replay. The default remains unchanged (orphaned telemetry), and this does not establish autonomous repair or generalized continuity.

The front-door source change causes the existing R1 byte-binding gate to report `AUTHORITY_FABRIC_BLOB_DRIFT` and `INVOCATION_AUTHORITY_FABRIC_BLOB_DRIFT`: 116 tests passed and the catalog structural-closure test failed in the four-suite targeted run. The full nine-module front-door workflow selection ran 82 tests: 79 passed and three failed on these same two drift errors (catalog, invoker catalog, and closure-gate assertions). Authority bindings have **not** been refreshed; doing so requires the repository's appropriate governance/verification process rather than simply rewriting hashes. The historical agent remains disconnected from live actions.

## Canary isolation research harness

`living_canary_isolation_v1.py` runs the actual `_canary_ok` from the four SHA-256-checked historical modules in a fresh Linux user/mount/network/PID namespace, in a chroot with a disposable work directory, a read-only bind of host `/usr`, only `/dev/null` exposed, and capabilities dropped before the worker runs. It fails closed if setup fails. `audit_living_canary_isolation_v1.py --living-source /path/to/trusted/snapshot` is an explicitly separate historical research control, not repository test infrastructure. On this machine, all nine checks passed: a valid canary passed, an incorrect expected result and escaping input were refused, caller fixtures stayed unchanged, and actual quoted `sed` paths that read and write a caller-owned sentinel outside the boundary could neither read nor write it inside the isolated canary. The bare control demonstrates why the historical shell's lexical path check is not an OS boundary.

This is **not** a production hostile-code sandbox: host `/usr` is readable, there is no seccomp policy or cgroup accounting, and resource/kernel attacks remain outside the tested boundary. It supports only canary evaluation with the pinned trusted Python implementation, not general historical agent actions or caller-supplied binaries. User namespaces may be unavailable; then it fails closed. More isolation, resource controls and end-to-end action tests are required before integration into a live creature. Repository unit tests run against the current implementation rather than importing the historical snapshot. Ten local isolated `wc` canaries took a median 121.87 ms (range 115.77–138.75 ms), including namespace, mount, Python startup and teardown; this is a small local timing sample, not an optimized production latency.

The current-tree continuity, replay, canary-harness unit, self-improvement, live runtime, queue, retained-skill, scoped benchmark and computer regressions passed **106 tests in 16.31 s** in the latest targeted run. The static integrity guard passed. These tests do not replace the separately reported nine-module front-door workflow result with three governance-binding failures.
