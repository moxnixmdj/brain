## Terminal target

Project Brain's terminal capability target is:

**OPUS_5_5_USEFUL_CAPABILITY_OWNERSHIP_V1**

The goal is to make the useful capabilities of Claude Opus 5.5 available to Brain at equal-or-better useful performance, with those capabilities durably configured, saved, inherited, and reusable by Brain without rediscovery.

The target is behavior, not imitation of Opus internals.

## Core theory

For Project Brain:

**EFFECTIVE FRONTIER INTELLIGENCE = PERMANENTLY OWNED CAPABILITIES + EXTERNAL JIT KNOWLEDGE**

Knowledge and capabilities are deliberately treated in opposite ways.

### Knowledge policy: externalize permanently

Knowledge is not accumulated as a giant permanent Brain knowledge warehouse.

When a task requires knowledge:
1. retrieve the strongest relevant current knowledge externally and just in time;
2. verify consequential claims as needed;
3. use it;
4. retain only evidence, provenance, decisions, compact state, or disposable caches needed for reproducibility and continuation.

A cache, citation archive, or retrieved fact is not a permanently acquired capability and receives no capability credit.

Brain may remember task state and evidence. It must not confuse that with a requirement to internalize the world's knowledge.

### Capability policy: acquire once, own permanently

Capabilities are the opposite.

For every useful Opus 5.5 capability:
1. identify the real useful behavior and acceptance bar;
2. search as broadly and quickly as possible for an already-existing realization;
3. require the configured result to equal or exceed the Opus 5.5 useful capability;
4. configure/integrate that realization into Brain;
5. verify the configured Brain capability;
6. save the complete capability package permanently;
7. inherit it globally so future work invokes it without capability rediscovery.

Routine task execution MUST NOT treat capabilities as JIT external knowledge.

A capability is not acquired merely because an external website, service, model, library, or tool can do it. It counts only after Brain has a durable configured route with a stable invocation contract, dependencies, version/configuration, recovery behavior, verifier, provenance, and regression evidence sufficient to reuse it as a Brain capability.

Remote execution may remain part of a configured implementation, but capability discovery and capability definition must not be repeated per task. The durable configured route is the owned capability.

## No-capability-invention law

The operating theory assumes the required useful capabilities already exist in realizable form somewhere.

Therefore:
- do not invent a new underlying useful capability;
- do not turn a capability-search failure into authorization to build the capability from first principles;
- building code is allowed only as integration glue, configuration, packaging, adapters, routing, persistence, verification, or recovery around an already-existing capability realization;
- if no existing equal-or-better realization can be found after adequate search, record an unresolved capability and a potential falsification of the theory. Do not silently move the goalposts.

## Opus 5.5 acceptance law

For target capability C:

**Capability(BrainConfigured(C)) >= Capability(Opus5.5(C))**

under the relevant useful conditions.

Anything weaker is not completion.

A weaker component may be used inside a composition, but the final configured Brain capability must meet or exceed the target behavior.

## Capability ownership package

A capability is permanently acquired only when Brain stores enough to invoke and maintain it without rediscovery, including:
- capability ID and useful behavior;
- Opus 5.5 comparison/acceptance bar;
- chosen existing realization(s);
- exact configuration and composition;
- local code/adapters/integration needed to invoke it;
- dependency/version/artifact identifiers where applicable;
- invocation contract;
- routing conditions;
- prerequisites;
- verification method and evidence;
- known failure modes;
- recovery/fallback behavior;
- cost/latency constraints;
- provenance;
- regression tests/evidence;
- durable inheritance path.

If these are absent, the capability is not yet ours.

## Correct operating sequence

### Capability acquisition phase

OPUS 5.5 CAPABILITY ENVELOPE
-> DEFINE ONE REAL USEFUL CAPABILITY
-> FIND EXISTING EQUAL-OR-BETTER REALIZATIONS
-> SELECT FASTEST SUFFICIENT ROUTE
-> CONFIGURE/INTEGRATE INTO BRAIN
-> VERIFY AGAINST OPUS 5.5 BAR
-> SAVE PERMANENT CAPABILITY PACKAGE

-> REPEAT

### Normal task execution phase

TASK
-> ROUTE TO ALREADY-OWNED BRAIN CAPABILITIES
-> RETRIEVE NEEDED KNOWLEDGE EXTERNALLY/JIT
-> EXECUTE
-> VERIFY CONSEQUENTIAL OUTPUT
-> PRESERVE EVIDENCE/STATE

Normal task execution is not the place to rediscover fundamental capabilities.

## Optimization law

Priority:
1. correctness and real useful capability;
2. equal-or-better than Opus 5.5;
3. minimum wall-clock time to permanent capability ownership;
4. $0 incremental spend unless explicitly changed by the user;
5. minimum compute/context/energy/complexity consistent with the above.

The fastest route is the route that makes an equal-or-better capability permanently ours soonest, not the route that produces the most infrastructure, tests, PRs, or local repairs.

## Anti-drift rules

Forbidden:
- treating capabilities as JIT resources;
- saying an external capability exists and counting that as Brain ownership;
- rediscovering the same capability per task;
- inventing a missing underlying capability;
- lowering the bar below Opus 5.5;
- treating knowledge caches as capability ownership;
- treating benchmark/probe activity as capability acquisition;
- perfecting a subordinate subsystem when a faster existing equal-or-better capability route can replace it;
- allowing a local subcapability frontier to become the terminal goal.

## Immediate program

1. recover the useful Opus 5.5 capability envelope;
2. map each capability to already-owned Brain capability, existing candidate realization, or unresolved search target;
3. search/race existing realizations in parallel where independent;
4. configure and save winners that meet/exceed the Opus 5.5 bar;
5. use external JIT knowledge during capability verification where knowledge is required;
6. keep each acquired capability permanently;
7. recompute until the useful Opus 5.5 capability envelope is owned by Brain.

## Mandatory pre-action question

Before every consequential action:

> Does this action make an Opus-5.5-or-better capability permanently ours faster, preserve/verify such ownership, or retrieve task knowledge JIT without confusing knowledge with capability?

If no, abort unless strictly required for correctness, evidence preservation, or canonical consistency.

## Theory falsification

This theory is not protected from evidence.

If adequate search shows a required Opus 5.5 useful capability has no realizable existing equal-or-better route under the hard constraints, record that result explicitly as a theory falsification candidate.

Do not solve the contradiction by redefining "existing", lowering the capability bar, or quietly authorizing invention.
