## Core theory

For Project Brain purposes, the useful power of a frontier model is decomposed into two broad sources:

**FRONTIER INTELLIGENCE = KNOWLEDGE + CAPABILITIES**

This is an operational decomposition, not a claim that neural models literally contain only two physical components.

### Knowledge side

The knowledge problem is treated as architecturally solved for the current program unless falsified:

Do not attempt to reproduce the frontier model's huge permanent knowledge store inside another parameter store.

Instead, obtain the strongest relevant knowledge when needed through authoritative retrieval, search, databases, documentation, tools, durable external memory, experiments, and other legitimate sources; verify and preserve what matters.

The achievement is not "less knowledge."

The achievement is:

> obtain equal or better useful knowledge faster and cheaper without requiring that all of it be permanently encoded in frontier-model parameters.

This is the precedent for the capability program.

### Capability side

The active research frontier is now the second term: **CAPABILITIES**.

For every useful capability demonstrated by frontier models or agents, do not begin by copying how the frontier model implements it.

Ask:

> What is the fastest and cheapest realizable way to obtain the maximum useful version of this capability, ideally equal to or better than the frontier?

Search every legitimate route.

A capability is **obsoleted** when a verified route provides the same relevant useful capability, or a stronger one, under the required real-world conditions such that reproducing the frontier model's expensive/internal way of providing that capability is no longer necessary.

Obsolescence does not mean the useful function disappears.
It means the frontier implementation or frontier-model-internal possession of that function is no longer required to obtain the useful capability.

## Optimization law

For each target capability C:

1. establish the useful frontier behavior F(C);
2. find a realizable route S(C);
3. require Capability(S(C), C) >= Capability(F(C), C) on the relevant real tasks;
4. among routes satisfying correctness and required capability strength, minimize:
   - wall-clock time to obtain/use the capability;
   - incremental monetary cost;
   - compute;
   - integration complexity;
   - permanent model requirements;
5. prefer a route that exceeds the frontier capability when available without violating higher-priority constraints.

The primary optimization target is therefore:

**maximum verified useful capability / minimum wall-clock time / minimum incremental cost**

with correctness first.

Hard project constraint remains:
- $0 incremental spend unless explicitly changed by the user.

## The obsolescence process

For every frontier capability:

1. **DEFINE THE REAL CAPABILITY**
   - describe what useful outcomes the frontier capability actually enables;
   - avoid model-name, benchmark, or implementation proxies.

2. **ESTABLISH THE FRONTIER BAR**
   - determine the strongest relevant demonstrated behavior we need to equal or exceed;
   - preserve uncertainty where the frontier bar is not directly measurable.

3. **SEARCH THE HIDDEN WAREHOUSE**
   - Project Brain's inherited capabilities;
   - algorithms;
   - libraries;
   - applications;
   - APIs;
   - databases;
   - search/retrieval;
   - formal solvers;
   - compilers/interpreters;
   - browsers/computer-use systems;
   - scientific software;
   - experiments/simulations;
   - specialized or smaller models;
   - frontier models as optional suppliers;
   - existing agent systems;
   - papers, repositories, documentation, and other legitimate public or connected sources.

4. **RACE THE BEST ROUTES**
   - direct reuse;
   - composition;
   - adaptation;
   - JIT acquisition;
   - specialized model/tool;
   - deterministic mechanism;
   - invention only after adequate existing routes are absent or inferior.

5. **TEST ON REAL WORK**
   - run consequential tasks that actually require the capability;
   - use hidden/unseen work when useful;
   - do not optimize an internal proxy.

6. **VERIFY**
   - independently verify the real outcome where consequential;
   - compare capability strength, correctness, latency, and cost under comparable conditions.

7. **OBSOLETE OR RETAIN**
   - if the substitute provides equal or better useful capability at the required conditions, mark the frontier implementation as obsolete for Project Brain;
   - if not, record the exact residual capability gap and continue only on that residual.

8. **INHERIT**
   - bind the winning route into the shared Brain;
   - preserve provenance, invocation contract, prerequisites, failure modes, verification, cost, latency, and regression evidence;
   - future workers consume the inherited route instead of rediscovering it.

9. **RECOMPUTE**
   - select the next capability whose obsolescence gives the highest expected useful capability gain per wall-clock time.

## What counts as progress

Progress exists when one or more of the following is independently supported:

- a frontier capability is matched or exceeded through a faster/cheaper route;
- a previously necessary frontier-model contribution is replaced by a verified external/JIT/composed mechanism;
- the residual frontier capability gap is narrowed and precisely localized;
- a stronger capability supplier is discovered and inherited;
- the same useful capability becomes available at materially lower latency, cost, compute, or model requirement without sacrificing correctness;
- one generic substitute obsoletes multiple frontier capability requirements at once;
- the capability-obsolescence machinery itself becomes faster or more general.

## What does NOT count as progress

- accumulating capability labels;
- matching an internal predicate by definition;
- passing a benchmark that does not establish the useful capability;
- reproducing the frontier implementation when a faster/cheaper route already exists;
- increasing parameter count;
- increasing worker count;
- adding infrastructure unrelated to the current capability-obsolescence frontier;
- claiming obsolescence through a weaker proxy;
- merely reducing dependence on a frontier model if useful capability strength falls below the frontier bar.

## Frontier capability maps

A frontier capability map is an **obsolescence queue**, not an acquisition checklist.

Its purpose is to answer:
- what useful capability does the frontier demonstrate?
- what is the current best known Project Brain route?
- how strong is it?
- how fast and cheap is it?
- is the frontier implementation already obsolete?
- what exact residual capability remains?

## Relationship to Superworkers

The verified Superworker architecture is the execution substrate for this program.

P_real = 1 proves one real integrated worker exists.

The current mission is not to scale copies of today's worker and not merely to make its capability inventory resemble a frontier model.

The worker is used to:
- discover capability routes;
- acquire/bind them;
- execute real tasks;
- verify results;
- inherit winners;
- continue the obsolescence process autonomously.

Clean-room reproduction remains necessary for architecture validity, but it is subordinate to the capability-obsolescence program and must not replace it as the terminal goal.

## Search-before-invention law

Never rebuild an expensive frontier capability merely because it can be rebuilt.

Search and compare existing mechanisms first.

Invent only when:
- no adequate existing route exists;
- existing routes violate hard constraints;
- composition/adaptation cannot reach the frontier bar;
- or invention is provably the fastest route to equal/better capability.

## Anti-proxy law

Obsolescence requires preserving the real useful behavior.

The following are forbidden substitutions:
- "we used fewer parameters" while capability degraded;
- "the benchmark passed" while real behavior did not;
- "the model is no longer called" while an equivalent expensive dependency was merely hidden elsewhere;
- "the task completed once" without evidence that the capability itself is reusable;
- "the route is cheaper" when it is materially weaker on the target capability.

## Mandatory pre-action question

Before every consequential action ask:

> Does this action directly help obtain an equal-or-better frontier capability faster/cheaper, prove that a candidate route does or does not reach the frontier bar, inherit a verified winning route, or remove the current causal blocker to doing so?

If NO, abort unless the action is strictly required for correctness, safety, evidence preservation, or canonical consistency.

## Priority

1. correctness and real capability;
2. minimum wall-clock time to equal-or-better capability;
3. minimum incremental cost;
4. minimum compute/context/energy and complexity consistent with the first three.

The goal is not to imitate frontier models.

The goal is to make their expensive ways of providing useful knowledge and capabilities unnecessary, one verified capability at a time.
