# A taught rule is not a shown rule

**2026-11-12.** Branch `arena/02b5ae8a-brain`. Authority **NONE**. `truth.achieved` = `false`.

## What was done, not argued

The auditability instrument reported `skills 0/5` — five stored rules, none re-checkable.
This pass found out *why* and moved the number.

### The defect, in one line

`crystallize_code_fix` stored `provenance = {before_sha256, after_sha256}`.

A **hash of the demonstration is history.** It identifies the source a rule was taught on but
cannot reproduce it, so a stored rule could never be re-executed. Measured from the live
database: **5 of 5 stored rules return `ABSENT / NO_TAUGHT_SOURCE`.**

### The fix

The same seam now also stores the text:

```python
rule['provenance'] = {
    'before_sha256': ..., 'after_sha256': ...,
    'taught_sources': [{'before': before_snippet, 'after': after_snippet}],
}
```

`canonical/swe_kernel/skill_recheck_v1.py` re-applies each stored rule to the source it was
taught on and returns a verdict that **can be FAIL**:

| verdict | meaning |
|---|---|
| `PASS` | re-applied now, still produces the stored rewrite |
| `FAIL` | it does not — the rule is stale, or the source moved under it |
| `ABSENT` | no source stored, so it can never be re-checked |

`ABSENT` is never counted as a pass. The command exits **1** on any `FAIL` and **2** when the
store itself cannot be read.

```
$ python3 -m canonical.swe_kernel.skill_recheck_v1
  5 stored rules
    PASS    0
    FAIL    0
    ABSENT  5
  recheckable: 0/5
```

A newly taught rule now returns `PASS` with `sources_checked: 1`.

### Tests — 10 new, all green, three of them prove FAIL

- a stale rule (stored rewrite no longer matches) → `FAIL / REWRITE_DIFFERS_FROM_TAUGHT`
- a source that moved under the rule → `FAIL / RULE_NO_LONGER_APPLIES`
- an applier that raises → `FAIL / APPLY_RAISED:RuntimeError`
- `ABSENT` is a missing measurement, never a pass
- a missing store reports `DB_ABSENT` and exits 2, not "0 rules"

## The bug this pass found in my own instrument

With no pytest installed, `test_modules` reported **`total 0, checkable 0`** — a confident
zero where the truth was "could not measure". Proven in a clean venv, and fixed: it now
returns `total: None, error: PYTEST_NOT_INSTALLED`, and there is a regression test.

That is the same failure class this whole line of work is about, appearing inside the
measuring tool: **a missing measurement is not a measurement of zero.**

## What the answer to the question now is, with a number attached

- **Before:** 5 rules, 0 re-executable, and the store could not have said otherwise.
- **Now:** new rules are re-executable and their PASS can become a FAIL; the five old rules
  stay `ABSENT` because the text was never kept, and the report says so instead of implying
  they are fine.

The next lesson taught by anything in this tree will arrive with the demonstration that
produced it, and `skill_recheck_v1` will be able to contradict it. That is the minimum
mechanism by which "learn it once, permanently" can be *checked* rather than asserted — and
without it the permanence mechanism amplifies whatever the check happens to see.
