# Computer execution route audit — 2026-11-02

This is a scoped source audit and producer-run experiment on the current working tree, not independent verification, admission, or a complete security review. The local worktree remains unadmitted. Do not run other routes against untrusted programs or valuable files on the strength of this audit.

## Reconciliation of the earlier composer results

For the previous 16 existing tests, the measured result was 8 passes, 6 failures and 2 errors. The observed failures/errors in those two classes and the unreachable-goal test all reached the **earlier type-level route** before the disabled exploration fallback: `route` returned `PASS__COMPOSER_ROUTE_FOUND`, not a result of doing the job. For example, the current graph routes `compress notes.txt into notes.txt.gz` to `shell.command.run` with inferred `gzip notes.txt`, and `archive notes.txt into notes.txt.zip` to a polyglot/build token. No requested output is produced by `route` itself. The nonsensical test goal reaches `python.source.symbol_index`. This explains why tests expecting discovered execution or an artifact fail even though their initial `pass` assertion may pass.

A later comparison ran these same 16 tests in separate disposable copies of base commit `2ececc45` and the current tree, both with the network namespace enabled. The same named tests produced 8 passes, 6 failures and 2 errors in each: these observed failures predate the draft. This does not imply all behavior is unchanged. The disabled fallback remains a real availability regression whenever it would otherwise be reached; forcing an empty graph demonstrates that it now refuses. Do not modify the tests to accept a plan as execution or claim this resolves the integration tests. The module docstring now distinguishes routing from execution.

## Composition verdict and retry audit

A later producer-run test exposed a separate issue: the controller's Tier 1 composition returned `pass=True` just because a chain reported execution success, without calling the raw-goal acceptance verifier. The front door's `_try_composed` also retained a provisional pass when acceptance was missing. The current unadmitted draft requires `semantic_acceptance_complete=True` on these two composed-success paths; an incomplete or failed check remains a failure. The controller also stops instead of trying a different tier after a failed dispatched step or an exception with uncertain effects. The front door retains that uncertainty and does not retry it. This is not proof that every acceptance verifier is sound, nor a sandbox or complete route audit.

A real text-write test in a disposable checkout produced `hello`, reopened it via the existing acceptance verifier, and passed; a wrong-content negative control was refused. These are producer-run tests and are not independent personnel verification. The stronger acceptance requirement can reduce availability where no verifier covers a chain; those cases need real verifiers, not waived assertions. Existing composer execution/solve integration tests produced 14 passes and 2 failures on both base and current trees; the two tests expect older result metadata. The earlier 6 failures and 2 errors remain unresolved.

**Correction to earlier interpretation:** an existing test expected a failing diagnosis request to remain unresolved. On this checkout the typed planner instead selected `software.analysis.diagnose_and_architect.v1`, and the result included the actual subtraction-vs-addition defect. The observed pass in that case was not evidence that no diagnosis existed. The test's older route assumption no longer held.

The reproduction revealed two different problems. First, this adapter's diagnosis operation runs the target test suite as host subprocesses, even though the adapter describes its work as read-only; other operations can also execute target code. A marker-writing test confirmed the host execution in a disposable network-only namespace. This draft refuses the entire known adapter on the examined local dispatcher, plan/DAG, composer, and raw-integrated entry paths, including aliases, before earlier steps run. The fabric/raw wrapper does not drain a repair queue after that particular boundary refusal. This is an availability regression, not a qualified carrier; direct adapter calls, the kernel's separate dispatch, other adapters and routes remain outside this partial guard.

Second, `_inspect_diagnose_and_architect` previously checked only producer flags, a parseable report and an operation string: a report whose root cause was fabricated, or absent, was accepted. New negative tests reproduce both. The inspector now refuses these diagnoses and the adapter's other report-only operations until operation-specific semantic verification exists; it does not pretend that refusal proves the underlying diagnosis was wrong. This broader refusal also reduces availability.

An earlier draft confinement test expected the door to return the recalled workflow's refusal after a prior attempt with uncertain effects. That expectation required calling `recall_and_execute_workflow`, which can also execute a different workflow. The test was updated to preserve its workflow-refusal assertion when the prior failure explicitly reports no possible effects, and to additionally assert that recall is never invoked when prior effects are uncertain. ## Carrier preparation: existing Docker launcher is a candidate, not a solution

`zero_ambient_authority_launcher_v1.py` generates `docker run` arguments for a digest-pinned image, no network, read-only root and input bind, dropped capabilities, non-root UID, and Docker CPU/memory/PID limits. Its six unit tests validate policy/argv/protocol shapes, not a live carrier. This environment has no Docker or delegated per-task cgroup access, so its existing live escape test cannot run here. No image was built, pulled, or asserted trustworthy.

Further issues to resolve before using it as an untrusted worker:

1. `run_confined` uses `subprocess.run(..., capture_output=True)` without an output-byte bound. A hostile child can exhaust the parent through stdout/stderr. `parse_effect_requests` has no count, size, schema, or artifact-content validation beyond basic JSON/type/id checks.
2. A timed-out Docker CLI is not in itself evidence that its daemon-managed container and descendants were killed and reaped. The current launcher does not explicitly identify and verify cleanup of its container. This needs real host tests, not a fake Docker binary.
3. A read-only `/input` is not sanitized input: policy accepts a caller-provided directory, and does not establish that nested mounts, credentials or unintended files are excluded. Image digest pinning identifies bytes but does not independently review their provenance or contents.
4. The launch plan does not explicitly pin and verify a seccomp profile, and effective isolation depends on daemon, kernel and carrier configuration. Existing escape tests mostly trust worker-reported observations; stronger host-side canaries and independent review are needed.
5. Material requests have **no authority** merely because they parse. A broker needs bounded messages, binding to the exact input and request, complete semantic verification, path/alias/race-safe no-overwrite publication, and explicit effect admission. Those pieces are not implemented by this audit.
