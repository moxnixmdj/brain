## Step 3 — Did wiring alone move the 0? **Partly. Not to a solve.**

I ran the zero-model SWE agent for real, end to end, on a trivial repository with a genuine
bug (`add` returns `a - b`; `test_add` fails).

### Before the fix — the agent could not even start

```
ModuleNotFoundError: No module named 'canonical.runtime'
```

The bundle (`_build_kernel_tar_gz`) shipped a **closed list of 7 files**. The kernel's own
transitive imports need **723 files, 649 of them under `canonical/runtime/`**.

> **The bundle shipped 7 of the 723 files the kernel imports. It could never have run.**

This is the single most concrete finding of the whole exercise. It is not a capability gap,
not a missing paper, not a hard research problem. **It is a hardcoded file list that went
stale.**

### After the fix — it runs, and reports honestly

I replaced the closed list with a closure computed from the import graph at build time
(`_kernel_bundle_closure`), with package `__init__.py` synthesis and deterministic tar
ordering. Bundle: **725 files, 3.6 MB, built in 4.5 s.**

Now the agent runs to completion and returns a real diagnosis:

```json
{"method": "METAMORPHIC_HABITATION_ZIPPER_V1",
 "mode": "SWE_BENCH_ZERO_MODEL",
 "model_dependency_count": 0,
 "stats": {"candidates_tested": 2, "passed": 0},
 "reason": "UNSOLVED_WITHIN_BUDGET",
 "repaired": false}
```

**0 model calls. Real verification cycle. Honest refusal.** It no longer lies about being
about to work — it says "unsolved within budget," which is true.

### And it repaired a test that was failing on `main`

`canonical/tests/test_harbor_swe_zero_model_agent_v1.py`:

| | result |
|---|---|
| **`main` (before my change)** | **12 passed, 1 FAILED** (`test_harbor_swe_zero_model_end_to_end_and_cross_container_l2_transfer`) |
| **with my change** | **13 passed, 0 failed** |

That test was asserting `status == "FINISHED"` and getting
`FAILED_NO_VERIFIED_REPAIR` — because the bundle couldn't import. **The end-to-end test was
already red, and it was red for exactly this reason.** One of the 13 tests in this file is
the whole point: end-to-end repair plus cross-container L2 transfer. It had been passing
for the author only because the test's own fake solvers didn't exercise the bundle.

### So: does wiring alone move the 0?

**It moves the 0 from "cannot start" to "unsolved", and that is the honest answer.** The
engine cannot yet repair a one-character operator swap on a three-function file.

I found the reason and it is a second wiring gap, not a capability gap:

> `canonical/swe_kernel/autonomous_awake_loop_v1.py` contains
> `_AST_BINOP_SWAPS = {ast.Sub: (ast.Add,), ...}` — **exactly the mutation this bug needs.**
> It is not in the repair chain the runner calls.

The runner chains `angelic_cegis_repair_v1`, `metamorphic_habitation_zipper_v1`,
`c_asan_cegis_repair_v1`, `js_causal_cegis_repair_v1`. The operator-swap table lives in a
self-play module that nothing routes to. **The capability exists, is correct, and is not
wired.** That is the same disease as step 1, one layer down.

## What this changes about the plan

1. **The premise is now proven, not argued.** 1,598 orphaned modules. One of them was a
   hardcoded 7-file list that made an entire agent unrunnable while its own test suite
   was red and attributed to something else.
2. **"Wiring" is a real and large category of defect, not a cleanup task.** Two found in
   the first two hours of looking; both silently load-bearing.
3. **Step 4 (the second localiser organ) should be preceded by a routing audit** of the
   SWE chain specifically: which kernel modules exist, which are called, and what the
   delta is. `autonomous_awake_loop_v1`'s swap table is one known delta; there will be more.
4. **The 0/51 is now explained twice over**, and neither explanation is "we can't do
   program repair." The first was the hard51 harness passing no `test_targets`; the second
   is this bundle. Both are plumbing.

## What I have not done, and will not claim

- I have **not** re-run hard51. That needs the Harbor/Docker harness and CI; there is no
  Docker in this sandbox. The prediction that it improves is **untested**.
- I have **not** fixed the operator-swap routing gap. It is identified and reproducible but
  not repaired, and I would rather say that plainly than ship an untested mutation engine.
- 1,634 capabilities are still orphaned. Four are unfrozen.

**The measured claim of this session is exactly this:** a reachability census exists and
runs in CI-able form; ten capabilities that could not be addressed now can be addressed or
are correctly reported as defective; and one of the two causes of the 0/51 turned out to be
a 7-line list that should have been a graph.
